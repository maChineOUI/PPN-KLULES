## 一、迁移动机与设计约束

### 1.1 为什么迁移到 Kokkos-Comm

原始 MPI 实现（W14）在功能上已经正确，但存在以下局限：

- 业务源文件（`lulesh-comm.cc`、`lulesh-timestep.cc`、`lulesh_main.cc`、`lulesh-init.cc`）直接包含 `<mpi.h>`，与特定运行时绑定
- `MPI_Request`、`MPI_Comm` 等类型污染了领域结构体 `DomainComm`
- 无法在同一代码路径下利用 Kokkos 的执行空间抽象（无 GPU-aware 通信语义）

Kokkos-Comm 提供以 `Kokkos::View` 为原生数据类型的点对点和集合通信接口，是 Kokkos 生态中实现"通信后端无关"的标准路径。

### 1.2 接口能力约束与关键设计决策

调研 Kokkos-Comm 0.2.0 源码快照（`2d1cd2c6`）后发现：

**约束**：顶层 `KokkosComm::send` / `KokkosComm::recv` 内部固定使用 tag `17`，**不暴露 tag 参数**。

**问题**：原实现依靠不同 tag（`MSG_COMM_SBN=1024`、`MSG_MONOQ=3072`）区分两类 halo 通信相位，若共用 communicator 且固定 tag，快进 rank 可能在下一 phase 串接前一 phase 消息。

**解决方案**：为每个 halo 相位单独 duplicate 一个 communicator：

```cpp
g_comm.sbnComm   = WorldComm().duplicate().value();
g_comm.monoqComm = WorldComm().duplicate().value();
```

MPI 消息匹配同时看 `(source, tag, communicator)`，communicator 不同则消息绝对不会串相。这一设计绕开了 tagged receive 接口缺口，同时使业务代码完全不接触 MPI 标签常量。

## 二、迁移架构

### 2.1 最终代码分层结构

迁移后代码严格分三层：

| 层 | 文件 | 职责 |
|----|------|------|
| **A 层（MPI 适配）** | `src/lulesh-runtime-mpi.cc` | 仓库中**唯一**允许调用 `MPI_*` 的文件 |
| **B 层（运行时接口）** | `include/lulesh-runtime.h` | 声明 `InitDistributedRuntime`、`BindWorldCommunicator`、`WorldComm()`、`DistributedRank()`、`DistributedSize()` |
| **C 层（业务代码）** | 其余所有文件 | 只调用 B 层接口和 `KokkosComm::*` |

### 2.2 新增文件

| 文件 | 作用 |
|------|------|
| `src/lulesh-runtime-mpi.cc` | MPI 初始化/析构；`BindWorldCommunicator` 将 `MPI_COMM_WORLD` 封装为 `KokkosComm::Communicator<MpiSpace, DefaultExecSpace>` |
| `include/lulesh-runtime.h` | B 层接口声明；定义 `DistributedComm` 类型别名 |

### 2.3 修改的文件

| 文件 | 核心变更 |
|------|---------|
| `CMakeLists.txt` | 新增 `find_package(KokkosComm)`；`KokkosComm_SOURCE_DIR` fallback；链接 `KokkosComm::KokkosComm` |
| `apps/lulesh_main.cc` | `MPI_Init/Finalize/Reduce` → `InitDistributedRuntime`、`BindWorldCommunicator`、`KokkosComm::Experimental::reduce` |
| `include/lulesh.h` | `DomainComm` 内部从 `MPI_Request[6]` 改为 `KokkosComm::Request<MpiSpace>[6]`；buffer 从 `Real_t*` 改为 `Kokkos::View<Real_t*, HostSpace>` |
| `include/lulesh-comm.h` | 新增 `CommTeardown()` 声明 |
| `src/lulesh-comm.cc` | **完全去除** `<mpi.h>`；用 `KokkosComm::send/recv/wait` 替代 `MPI_Isend/Irecv/Waitall` |
| `src/lulesh-timestep.cc` | 2 处 `MPI_Allreduce(MIN)` 合并为 1 次 `KokkosComm::Experimental::allreduce(Min{})` |
| `src/lulesh-init.cc` | `MPI_Comm_rank()` 改为 `DistributedRank()` |

## 三、核心实现细节

### 3.1 运行时初始化顺序（两段式）

```cpp
InitDistributedRuntime(argc, argv);    // 1. MPI_Init_thread / MPI_Comm_rank/size
Kokkos::initialize(argc, argv);        // 2. Kokkos 初始化（需先有 MPI）
{
  BindWorldCommunicator(Kokkos::DefaultExecutionSpace{});  // 3. 绑定 world communicator
  // ...
  CommTeardown();                      // 4. 释放 duplicate communicator（在 MPI_Finalize 之前）
} // end Kokkos scope
Kokkos::finalize();                    // 5.
FinalizeDistributedRuntime();          // 6. MPI_Finalize
```

`CommTeardown()` 在 `MPI_Finalize` 前调用是硬约束：`sbnComm`/`monoqComm` 析构时调用 `MPI_Comm_free`，必须早于 `MPI_Finalize`。

### 3.2 DomainComm 新结构

```cpp
struct DomainComm {
  using Exec = Kokkos::DefaultExecutionSpace;
  using Comm = KokkosComm::Communicator<KokkosComm::MpiSpace, Exec>;
  using Req  = KokkosComm::Request<KokkosComm::MpiSpace>;

  std::optional<Comm> sbnComm;         // SBN 相位专用
  std::optional<Comm> monoqComm;       // MONOQ 相位专用

  Kokkos::View<Real_t*, Kokkos::HostSpace> sendBuf;
  Kokkos::View<Real_t*, Kokkos::HostSpace> recvBuf;

  std::array<Req, 6> recvReq;
  std::array<Req, 6> sendReq;
};
```

buffer 由原始 `new[]` 改为 `Kokkos::View<..., HostSpace>`，生命周期随 `optional` 自动管理，可用 `Kokkos::subview` 切取 face 子区间传给 `KokkosComm::send/recv`。

### 3.3 halo 通信流程迁移

以 `CommSend` 为例（`CommRecv` 完全对称）：

```cpp
// 选择相位 communicator
auto& phaseComm = (msgType == MSG_COMM_SBN) ? *g_comm.sbnComm : *g_comm.monoqComm;

// 打包（逻辑与原版完全相同，不变）
// ...

// 发送：取 subview，非阻塞发出
auto slice = Kokkos::subview(g_comm.sendBuf, std::make_pair(offset, offset + count));
g_comm.sendReq[face] = KokkosComm::send(phaseComm, slice, dstRank);
```

`CommSBN`/`CommMonoQ` 中改为逐个 `KokkosComm::wait()`，而非 `MPI_Waitall`，原因是 `wait_all` 在 Kokkos-Comm 0.2.0 中不会将 request 置为可复用状态，逐个 wait 行为更可控。

### 3.4 集合通信迁移

`TimeIncrement` + `CalcTimeConstraintsForElems` 中原有 3 次 `MPI_Allreduce(MIN)` 合并为 1 次：

```cpp
Kokkos::View<Real_t*, Kokkos::HostSpace> send("dt_pair_send", 2);
Kokkos::View<Real_t*, Kokkos::HostSpace> recv("dt_pair_recv", 2);
send(0) = dtc;  send(1) = dth;
KokkosComm::Experimental::allreduce(WorldComm(), send, recv, KokkosComm::Min{}).wait();
domain.dtcourant() = recv(0);
domain.dthydro()   = recv(1);
```

`lulesh_main.cc` 中 elapsed time 归约：

```cpp
KokkosComm::Experimental::reduce(WorldComm(), elapsed_send, elapsed_recv, 0, KokkosComm::Max{}).wait();
```

## 五、技术决策总结

### 5.1 Communicator Duplication 替代 Message Tag

最核心的设计选择。Kokkos-Comm 0.2.0 的顶层 point-to-point 接口不暴露 tag，若两个 halo 相位共用同一 communicator 且固定 tag，则在 rank 速度不均时有串相风险。通过为 `sbnComm`/`monoqComm` 各自 duplicate 独立 communicator，彻底解决了 tag 接口缺口，同时保持业务代码对 MPI 细节的完全无感知。

### 5.2 两段式初始化

`Communicator<MpiSpace, ExecSpace>` 需绑定一个已存在的 Kokkos execution space，因此 MPI 初始化（`InitDistributedRuntime`）和 communicator 绑定（`BindWorldCommunicator`）分为两个独立调用，中间插入 `Kokkos::initialize`。这是一个不可绕过的生命周期约束。

### 5.3 DomainComm buffer 改为 HostSpace View

原始 `new[] Real_t` 改为 `Kokkos::View<Real_t*, HostSpace>`，好处：（a）生命周期与 `optional<Comm>` 一致，无需手动 `delete[]`；（b）可直接用 `Kokkos::subview` 切取 face 对应区间传给 `KokkosComm::send/recv`，与 Kokkos-Comm 的 View 语义无缝对接。

### 5.4 逐个 wait 而非 wait_all

Kokkos-Comm 0.2.0 的 `wait_all` 实现会复制底层 `MPI_Request`，原 request 对象不会自动置为可复用状态。为保持行为可控、便于调试，本实现统一采用逐个 `KokkosComm::wait()`。

## 八、CPU+MPI 性能与 GitHub 官方基线对比

本周在 GitHub 官方基线对照验证通过后，对 CPU+MPI（`OMP_NUM_THREADS=1`）路径进行了初步性能对比，确认迁移后无系统性性能退化。

### 8.1 测试方法

- 官方基线：`LLNL/LULESH` tag `2.0.3`，commit `46c2a1d6`，本地从源码重建
- 当前版本：`build-kokkos-comm/lulesh2.0`
- 统一参数：`--bind-to none -x OMP_NUM_THREADS=1 -x OMP_PROC_BIND=false`
- 每组各运行 3 次，取中位数 FOM（zone-updates/second）

| Case | rank | 参数 | 基线中位 FOM | 当前中位 FOM | 结论 |
|------|-----:|------|------------:|------------:|------|
| M1 | 1 | `-i 20 -s 50` | 2387.4 | 2455.4 | 当前略快 +2.9% |
| M2 | 8 | `-i 20 -s 30` | 8146.3 | 7811.0 | 当前略慢 −3.8% |
| M3 | 27 | `-i 20 -s 20` | 9677.3 | 10404.9 | 当前略快 +7.5% |

数值一致性：三组 case 的 `Final Origin Energy` 在两侧完全相同，`MaxRelDiff` 仅在 `1e-13～1e-11` 量级（双精度舍入范围）。

### 8.2 结论

当前 Kokkos-Comm 版本在 CPU+MPI 路径上的性能总体与 GitHub 官方 LULESH 2.0 持平。8-rank M2 case 有约 3.8% 的轻微回退，但绝对 wall-time 差距极小（0.02 s 量级），后续通过代码优化（P1–P6）可进一步消除。
