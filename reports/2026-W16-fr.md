# Rapport hebdomadaire 2026-W16 | LULESH 2.0 Migration GPU : Optimisations post-Kokkos-Comm et analyse du chevauchement de communication

**Période** : 2026-04-13 ~ 2026-04-19
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU)
**Plateforme** : macOS Apple Silicon (validation locale) ; cible : Linux + NVIDIA GPU (backend CUDA)
**Référence cette semaine** : version Kokkos-Comm de W15 (`build-mpi` raw-MPI utilisé comme référence de comparaison)
**Conclusion** : Six optimisations P1–P6 déployées, FOM en hausse de +10,9 % à +24,0 % ; infrastructure de profilage établie ; MonoQ plane recv identifié comme goulot principal 8-rank ; expériences T1/T2 validées en première passe ; optimisations O1/O2/O3 dt allreduce invalidées par test à variable unique et annulées (retour à KokkosComm) ; cinq corrections de qualité de code appliquées

---

## Vue d'ensemble

Cette semaine, à partir de la base Kokkos-Comm de W15 : (1) six optimisations de code P1–P6 ont été déployées (suppression de noyaux redondants, amélioration du cycle de vie des views, restructuration des chemins de pack/write-back) ; (2) une infrastructure de profilage dédiée a été mise en place (build-profile) avec instrumentation fine ; (3) les points chauds CPU+MPI 8-rank ont été analysés systématiquement, identifiant MonoQ plane recv comme goulot principal ; (4) deux cycles d'optimisation du chevauchement ont été implémentés et validés (T1 : post recv anticipé, T2 : calcul boundary en deux étapes) ; (5) trois optimisations du dt allreduce (O1/O2/O3) ont été finalisées, apportant +10,5 % de FOM supplémentaire sur chemin CPU et posant l'infrastructure Iallreduce/split-nœuds pour le chemin GPU.

---

## I. Optimisations de code P1–P6

### 1.1 Liste des optimisations

Six améliorations de code ont été appliquées sur la version Kokkos-Comm de base. Chacune garantit l'équivalence mathématique ; la correction a été vérifiée sur la matrice B1–B5 complète.

| N° | Nom | Modification principale | Bénéfice |
|----|-----|------------------------|---------|
| P1 | Suppression du contrôle de volume redondant | Suppression du noyau `CalcVolumeForceForElems_check` (contrôle `vnew ≤ 0` déjà effectué dans `CalcLagrangeElements`) | −1 kernel launch/pas |
| P2 | Restauration de RangePolicy sur chemin non-MPI | Suppression de la reconstruction temporaire `allElemsIdx` sur le chemin `USE_MPI=0` | −1 kernel launch + alloc temporaire/pas |
| P3 | Pré-allocation des mirror views SBN | Ajout de `sbn_fx_h/fy_h/fz_h` dans `DomainComm`, alloués une fois dans `CommSetup` | −~715 Ko malloc/pas |
| P4 | Pré-allocation de vnew + determ | `m_vnew`/`m_determ` persistants dans `Domain`, alloués à l'initialisation | −~432 Ko malloc/pas |
| P5 | Pré-allocation des tampons scatter | Struct `ScatterBuffers` avec 6 tableaux `fx/fy/fz/hg_fx/hg_fy/hg_fz` (taille `numElem×8`) ; `IntegrateStressForElems` et `CalcHourglassControlForElems` utilisent ces tampons pré-alloués | −~10,4 Mo malloc/pas (poste le plus important) |
| P6 | Fusion des trois noyaux ApplyBC | Regroupement des trois `parallel_for` X/Y/Z en un seul | −2 kernel launches/pas |

### 1.2 Structure ScatterBuffers (noyau de P5)

```cpp
struct ScatterBuffers {
    Kokkos::View<Real_t*> fx,    fy,    fz;
    Kokkos::View<Real_t*> hg_fx, hg_fy, hg_fz;
    void reserve(Index_t numElem8) {
        fx    = Kokkos::View<Real_t*>("fx_elem",    numElem8);
        fy    = Kokkos::View<Real_t*>("fy_elem",    numElem8);
        fz    = Kokkos::View<Real_t*>("fz_elem",    numElem8);
        hg_fx = Kokkos::View<Real_t*>("hg_fx_elem", numElem8);
        hg_fy = Kokkos::View<Real_t*>("hg_fy_elem", numElem8);
        hg_fz = Kokkos::View<Real_t*>("hg_fz_elem", numElem8);
    }
} m_scatter;
```

### 1.3 Structure DomainComm finale (état fin de semaine)

Après implémentation puis annulation de O1/O2/O3, la structure finale conserve `dt_send_pair`/`dt_recv_pair` (requis par l'allreduce KokkosComm) et supprime les champs O3 `interiorNodes`/`boundaryNodes`.

```cpp
struct DomainComm {
    using execution_space   = Kokkos::DefaultExecutionSpace;
    using communicator_type = KokkosComm::Communicator<KokkosComm::MpiSpace, execution_space>;
    using request_type      = KokkosComm::Request<KokkosComm::MpiSpace>;
#ifdef KOKKOS_ENABLE_CUDA
    using buffer_type = Kokkos::View<Real_t*, Kokkos::CudaHostPinnedSpace>;
#else
    using buffer_type = Kokkos::View<Real_t*, Kokkos::HostSpace>;
#endif
    std::optional<communicator_type>  sbnComm, monoqComm;
    buffer_type  sendBuf, recvBuf;
    std::array<request_type, 6> recvRequest, sendRequest;
    // Tampons de staging pour l'allreduce KokkosComm (contrainte dt)
    buffer_type  dt_send_pair, dt_recv_pair;
    // Miroirs hôte persistants (P3/O-B)
    buffer_type  monoq_dxi_h, monoq_deta_h, monoq_dzeta_h;
    buffer_type  sbn_fx_h, sbn_fy_h, sbn_fz_h;
    // T2 : index d'éléments boundary par étape (chevauchement en 3 phases)
    Kokkos::View<Index_t*> interiorElems, rowColBoundaryElems, planeBoundaryElems;
};
```

## IV. Chaîne d'analyse des points chauds 8-rank

### 4.1 Profilage ciblé (1er cycle)

Configuration : `8 ranks, OMP=1, -i 50 -s 30/40`, 5 répétitions.

| Timer | D1 médiane ms/pas | D1 part | Remarque |
|-------|------------------:|-------:|---------|
| `dt_allreduce` | 3,247 | 12,07 % | Réduction globale par pas |
| `sbn_wait_unpack` | 2,147 | 8,15 % | Phase SBN attente+déballage |
| `commsbn_wait` | 2,105 | 7,99 % | Attente effective SBN |
| `monoq_wait_unpack` | 1,909 | 7,22 % | Phase MonoQ attente+déballage |
| `commmonoq_wait` | 1,778 | 6,72 % | Attente effective MonoQ |
| `commsend_pack` | 0,054 | 0,20 % | Emballage (négligeable) |

Observations clés :
- **L'attente est bien supérieure au déballage** : SBN `wait/unpack ≈ 64:1` ; MonoQ `wait/unpack ≈ 178:1`
- **L'emballage est négligeable** : 0,2 % seulement
- **Le staging hôte est faible** : sur chemin CPU-only, `sbn_host_pull/push` ≈ 0,1–0,3 % chacun
- **`dt_allreduce` est un second point chaud** : ~12 % du temps par pas

Conclusion : le principal goulot d'étranglement 8-rank est l'**exposition de l'attente MPI**, pas l'emballage ni le staging.

### 4.2 Analyse du chevauchement MonoQ (2e cycle)

Ligne dérivée `monoq_overlap` ajoutée pour analyser la fenêtre de calcul interior vs attente résiduelle.

| Indicateur | D1 médiane | D2 médiane |
|------------|----------:|----------:|
| `window_ms` (calcul interior) | 0,491 | 1,262 |
| `recv_wait_ms` (attente résiduelle) | 1,974 | 3,625 |
| `send_wait_ms` | 0,005 | 0,008 |
| `residual_sync_to_window` | ~3,99 | ~2,91 |

- `window:wait ≈ 1:4` (D1) : la fenêtre de calcul interior ne couvre qu'environ 25 % de l'attente de réception
- `send_wait` négligeable ; l'exposition provient essentiellement de `recv`

## V. Expériences d'optimisation du chevauchement MonoQ

### 5.1 T1 : anticipation du post CommRecv(MSG_MONOQ)

**Modification** : déplacement de `CommRecv(domain, MSG_MONOQ, ...)` avant `CalcMonotonicQGradientsForElems()` pour que le message de réception entre plus tôt en vol.

**Résultats profil A/B** (D1/D2, 5 répétitions chacun, baseline = version sans T1) :

| Indicateur | D1 baseline | D1 T1 | D2 baseline | D2 T1 |
|------------|------------:|------:|------------:|------:|
| `plane_min recv_wait_fraction` | 0,644 | 0,421 | 0,556 | 0,312 |
| `plane_max recv_wait_fraction` | 0,630 | 0,381 | 0,571 | 0,320 |
| `plane_min recv_hidden_ms` | — | +167 % | — | +153 % |
| `plane_max recv_hidden_ms` | — | +185 % | — | +160 % |

**Résultats release A/B** (R1/R2, 7 répétitions, `/usr/bin/time -p`) :

| Cas | baseline médiane | T1 médiane | Évolution |
|-----|----------------:|----------:|-----------|
| R1 (s=30, 7 répét.) | 1,46 s | 1,47 s | +0,68 % |
| R2 (s=40, 7 répét.) | 3,02 s | 3,07 s | +1,66 % |

**Conclusion** : T1 améliore nettement le cycle de vie de la réception plane en profil (`recv_wait_fraction` −0,22–0,25, `recv_hidden_ms` +150–185 %), mais cette amélioration ne se traduit pas encore en gain de temps wall. La direction mécaniste est correcte, mais la fenêtre de calcul interior reste insuffisante pour absorber les réceptions avancées.

### 5.2 T2 : boundary en deux étapes — calcul row/col puis plane

**Modification** : découpage du calcul boundary en trois phases, élargissant la fenêtre de travail utile pendant le vol de la réception plane :

```
1. CommRecv(MSG_MONOQ) anticipé
2. CalcMonotonicQGradientsForElems
3. Pull hôte + CommSend(MSG_MONOQ)
4. Calcul interiorElems (sans dépendance ghost)
5. CommMonoQRowCol : attente/déballage faces row/col → push ghosts row/col vers device
6. Calcul rowColBoundaryElems (dépend uniquement des ghosts row/col)
7. CommMonoQPlane : attente/déballage faces plane → push ghosts plane vers device
8. Calcul planeBoundaryElems (dépend des ghosts plane)
```

**Fichiers modifiés** : `src/lulesh-comm.cc`, `src/lulesh-viscosity.cc`, `include/lulesh.h`, `include/lulesh-comm.h`, `include/lulesh-profile.h`, `src/lulesh-profile.cc`

**Vérification de correction** :

- `1 rank, -i 1 -s 5` : `Final Origin Energy = 5.416661e+04`, `MaxAbsDiff = 0`
- `8 ranks, -i 1 -s 3` : `Final Origin Energy = 9.359991e+04`, `MaxAbsDiff = 0`

**Résultats de profilage initial** (`8 ranks, OMP=1, -i 10 -s 30`) :

| Indicateur | T1 (référence) | T2 |
|------------|---------------:|----|
| `plane_min recv_wait_fraction` | ~0,42 | **0,108** |
| `plane_max recv_wait_fraction` | ~0,38 | **0,029** |
| Face pic `monoq_face_wait_peak` | `plane_min/plane_max` | **`row_max`** |

`recv_wait_fraction` passe de ~0,4 avec T1 à ~0,03–0,11 avec T2 ; la face la plus lente bascule de plane vers row — signal très encourageant. La conclusion formelle sur les performances reste à établir via les tests A/B.

## VI. Optimisations dt allreduce (O1/O2/O3)

### 6.1 Contexte

Les données de profilage (8 ranks, s=30) indiquent que `dt_allreduce` (la réduction globale de contrainte dt dans `CalcTimeConstraintsForElems`) représente 12–15 % du temps par pas, avec un déséquilibre de 1,58. L'implémentation originale utilisait `KokkosComm::Experimental::allreduce` avec des tampons View KokkosComm, ajoutant des allocations mémoire et un surcoût d'ordonnancement inutiles.

### 6.2 Description des trois optimisations

| N° | Nom | Chemin | Modification principale |
|----|-----|--------|------------------------|
| O1 | `MPI_Allreduce` brut | CPU (livré) | Deux `double` sur la pile + `MPI_Allreduce(…, 2, MPI_DOUBLE, MPI_MIN, …)` ; suppression des View `dt_send_pair`/`dt_recv_pair` |
| O2 | Pipeline `MPI_Iallreduce` | GPU (`KOKKOS_ENABLE_CUDA`) | `MPI_Iallreduce` non bloquant lancé en fin de `CalcTimeConstraintsForElems` ; `WaitDtIallreduce` + `TimeIncrement` appelés dans `LagrangeNodal` avant `CalcVelocity` ; fenêtre de chevauchement ~12 ms |
| O3 | Split nœuds SBN interior/boundary | GPU (`KOKKOS_ENABLE_CUDA`) | `CommSetup` construit `interiorNodes`/`boundaryNodes` ; `CalcAccelerationForNodes(interiorNodes)` lancé sur le device pendant l'attente CommSBN ; les nœuds boundary attendent la fin du scatter-add |

**Pourquoi O2/O3 sont réservés au GPU** : sur CPU, supprimer la barrière implicite de l'allreduce désynchronise les ranks ; `sbn_wait_unpack` passe de 2,08 ms à 6,28 ms (+4,2 ms), dépassant le gain allreduce de 2,6 ms. Sur GPU, les noyaux device s'exécutent en parallèle avec le thread de progression MPI — ce problème n'existe pas.

### 6.3 Fichiers modifiés

| Fichier | Modification |
|---------|-------------|
| `include/lulesh-runtime.h` | Déclarations `PostDtIallreduce(double, double)` / `WaitDtIallreduce(double&, double&)` |
| `src/lulesh-runtime-mpi.cc` | `RuntimeState` : `MPI_Request dt_req`, `double dt_send[2]`, `double dt_recv[2]` ; implémentations `PostDtIallreduce`/`WaitDtIallreduce` ; drain dans `FinalizeDistributedRuntime` |
| `include/lulesh.h` | `DomainComm` : suppression `dt_send_pair`/`dt_recv_pair` ; ajout `interiorNodes`/`boundaryNodes` |
| `src/lulesh-comm.cc` | `CommSetup` : suppression allocations View dt ; ajout boucle de construction `interiorNodes`/`boundaryNodes` ; `CommTeardown` mis à jour |
| `src/lulesh-timestep.cc` | `#ifdef KOKKOS_ENABLE_CUDA` : `PostDtIallreduce` non bloquant ; `#else` : `MPI_Allreduce` bloquant avec `ProfileScope` |
| `src/lulesh-nodal.cc` | Surcharge `CalcAccelerationForNodes(domain, nodeList)` ; chemin GPU : split O3 + `WaitDtIallreduce`+`TimeIncrement` (O2) |
| `apps/lulesh_main.cc` | Chemin GPU-MPI : `TimeIncrement` supprimé de la boucle principale (intégré dans `LagrangeNodal`) |

### 6.4 Résultats de performance (CPU, 8 ranks, s=30, 100 pas)

| Timer | T1 baseline | Après O1 | Évolution |
|-------|------------:|---------:|-----------|
| `step_total` | 34,24 ms | **30,99 ms** | **−3,25 ms (−9,5 %)** |

### 6.6 Test à variable unique et annulation

**Découverte** : le build O1 de la section 6.4 incluait simultanément T2 (staged MonoQ boundary). Le gain +10,5 % de FOM était un effet combiné ; il restait à isoler la contribution propre de O1. Un binaire à variable unique a été construit en remplaçant uniquement deux fichiers objets (`lulesh-timestep.cc.o` et `lulesh-runtime-mpi.cc.o`) dans le build de référence T1.

**Résultat du test à variable unique** (8 ranks, s=30, 7 répétitions alternées) :

| Build | FOM médian (z/s) | CV |
|-------|----------------:|-----|
| T1 baseline | 6 309 | 1,1 % |
| O1 seul | 6 315 | 1,3 % |
| **Écart** | **+0,1 %** | dans le bruit de mesure |

**Source de la confusion** : la baisse de `monoq_wait_unpack` de 2,24 ms à 0,29 ms (−1,95 ms) était la contribution de T2, non d'O1. L'économie allreduce d'O1 (~2,6 ms/pas) réduit une latence intermédiaire mais ne raccourcit pas le chemin critique du step.

**Décomposition du surcoût KokkosComm allreduce** (route `mpi::iallreduce`) :

| Poste | Contenu |
|-------|---------|
| MPI effectif | `MPI_Iallreduce` + `MPI_Wait` |
| Fence supplémentaire | `space.fence()` |
| Extension durée de vie view | `extend_view_lifetime` × 2 (alloc tas + ref. atomique × 4) |
| Hooks Kokkos Tools | `pushRegion` / `popRegion` |

Ces surcoûts représentent ~1–2 ms/pas mais, comme l'allreduce est déjà un point de synchronisation global, les économiser ne modifie pas la longueur du chemin critique.

**Cause de la régression O2 sur CPU** : supprimer l'allreduce bloquant désynchronise les ranks ; `sbn_wait_unpack` passe de 2,74 ms à 6,28 ms (+4,2 ms), dépassant l'économie allreduce de 2,6 ms — perte nette de −25,9 % de FOM (s=30).

**Décision d'annulation** : O1/O2/O3 entièrement annulés, retour à `KokkosComm::Experimental::allreduce`. Fichiers restaurés : `src/lulesh-timestep.cc`, `src/lulesh-nodal.cc`, `apps/lulesh_main.cc`, `include/lulesh-runtime.h`, `src/lulesh-runtime-mpi.cc`, `src/lulesh-comm.cc`. Les deux builds (`build-kokkos-comm`/`build-profile`) compilent proprement après retour arrière.

## VII. Corrections de qualité de code

Cinq défauts hérités de LULESH 2.0 original ont été identifiés lors de l'audit de migration et corrigés.

### 7.1 Sécurité MPI multi-processus : `exit` → `MPI_Abort`

**Problème** : dans `CalcQForElems`, si la viscosité artificielle dépasse `qstop`, `exit(QStopError)` n'arrête qu'un seul rank, laissant les autres suspendus indéfiniment en attente de communication MPI.

**Correction** (`src/lulesh-viscosity.cc`) :

```cpp
// Avant
if(idx >= 0) { exit(QStopError); }

// Après
if(idx >= 0) {
#if USE_MPI
    MPI_Abort(MPI_COMM_WORLD, QStopError) ;  // arrêt collectif de tous les ranks
#else
    exit(QStopError) ;
#endif
}
```

### 7.2 Pré-allocation des gradients et déformations

**Problème** : `CalcQForElems` appelait `AllocateGradients` (6 views) + `DeallocateGradients` et `CalcLagrangeElements` appelait `AllocateStrains` (3 views) + `DeallocateStrains` à chaque pas — soit 9 malloc/free Kokkos View par itération pour des tailles fixes.

**Correction** : `AllocateGradients` et `AllocateStrains` déplacés dans le constructeur `Domain` (`src/lulesh-init.cc`) ; appels par pas et méthodes `Deallocate*` supprimés de `include/lulesh.h`.

### 7.3 Code mort après `Kokkos::abort()` dans les kernels GPU

**Problème** : les branches `default` des `switch` dans `CalcMonotonicQForElems` et `CalcMonotonicQForElemsSubset` contenaient `delvm=0; break;` après `Kokkos::abort()`. Sur GPU, `__trap()` ne garantit pas l'arrêt immédiat du flux d'exécution ; si le compilateur n'honore pas la sémantique `[[noreturn]]`, l'assignation peut être effectuée, propageant 0 à la place du gradient voisin correct.

**Correction** (`src/lulesh-viscosity.cc`, 12 emplacements) : suppression de l'assignation et du `break` après chaque `Kokkos::abort()`.

### 7.4 Suppression du paramètre mort `planeOnly`

**Problème** : `CommRecv` et `CommSend` avaient un paramètre `bool planeOnly` jamais lu, toujours passé à `false` dans les 4 appels — interface réservée de LULESH 2.0 jamais implémentée.

**Correction** : paramètre supprimé de la déclaration (`include/lulesh-comm.h`), de la définition (`src/lulesh-comm.cc`) et des 4 sites d'appel (`src/lulesh-nodal.cc`, `src/lulesh-viscosity.cc`).

### 7.5 Assertion de domaine cubique

**Problème** : `numNodeBC = (sizeX+1)²` dans `ApplyAccelerationBoundaryConditionsForNodes` — hypothèse implicite que le domaine est cubique (sizeX == sizeY == sizeZ) ; un domaine non cubique provoquerait un accès hors limites silencieux sur les plans symmY/Z.

**Correction** (`src/lulesh-nodal.cc`) :

```cpp
assert(domain.sizeY() == size && domain.sizeZ() == size
       && "ApplyBC: symmetry plane nodesets assume a cubic domain") ;
```
