# 周报 2026-W11 | LULESH 2.0 多线程并行效率回归诊断与优化

**周期**：2026-03-09 ~ 2026-03-15
**项目**：LULESH 2.0 高性能计算代理应用（Kokkos 5 / OpenMP 后端）
**平台**：macOS Apple Silicon（4 P-core + 6 E-core）
**正确性基准**：`OMP_PROC_BIND=close ./build/release/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## 一、问题发现

上一周完成 Kokkos 5 迁移及两轮内核融合（累计加速比 2.15×）后，开展多线程扩展性测试，发现一个反常现象：

**测试条件**：`-s 45 -i 100`，`OMP_PROC_BIND=close`，Apple M 系列处理器

### 优化前扩展性数据

| 线程数 | 耗时 | 加速比（相对 T=1） | 备注 |
|--------|------|--------------------|------|
| T=1    | 2.76 s | 1.00× | 全 P-core |
| T=2    | 1.75 s | 1.58× | 全 P-core |
| T=4    | 1.25 s | **2.21×** | 全 P-core，最优点 |
| T=5    | 1.53 s | 1.80× | **性能倒退 22%** |
| T=6    | 1.45 s | 1.90× | 含 E-core |
| T=8    | 1.39 s | 1.99× | 含 E-core |
| T=10   | 1.46 s | 1.89× | 含 E-core |

**关键异常**：T=4 → T=5 时，耗时从 1.25 s 增至 1.53 s，性能下降 22%。这与"线程数增加性能单调提升"的通常预期相悖。

## 二、根本原因分析

### 原因一：P/E 异构核心导致屏障不均衡（主因）

Apple Silicon 的物理拓扑为 **4 P-core（高性能）+ 6 E-core（能效）**。两类核心的峰值时钟频率相差约 40%，L2 缓存容量也不同。

Kokkos `parallel_for` 和 `parallel_reduce` 在结束时均有**隐式全量屏障（full barrier）**——等待所有线程完成当前内核后才继续下一个内核。当 T=4 时，四条线程全部运行在 P-core 上，屏障等待时间极短；当 T=5 时，第五条线程被 OS 调度到 E-core，处理相同工作量需要更长时间，**所有 P-core 线程在每个屏障处都要等待这一条慢线程**。

原始 LULESH 2.0 广泛使用 `#pragma omp for nowait`，允许 P-core 线程在完成当前循环后立即进入下一个循环，而不必等待 E-core 追上。本项目的 Kokkos 版本将每段 `omp for` 独立封装为一个 `Kokkos::parallel_for`，消除了 `nowait` 语义，使 E-core 的延迟在每个屏障处完全暴露。

```
T=4（全 P-core）：
  P P P P ──── kernel ────|barrier|──── kernel ────  快速

T=5（4P + 1E）：
  P P P P ── kernel ──|等待|barrier|── kernel ──     每个屏障多等 22%
                 E  ──────── kernel ────────|
```

### 原因二：EOS 模块频繁堆内存分配（次因）

`EvalEOSForElems`（[src/lulesh-eos.cc](src/lulesh-eos.cc)）在每个 region、每次 rep 循环内：

```cpp
std::vector<Real_t> e_old(numElemReg);   // × 14 个临时向量
std::vector<Real_t> delvc(numElemReg);
// ... 共 14 个
```

对于 `-s 45 -i 200`（11 个 region，约 5 次 rep 均值，200 步）：
- 分配次数：11 × 5 × 200 × 14 ≈ **154,000 次 malloc/free**
- 多线程下，glibc/libmalloc 的全局锁在竞争时会导致串行化，线程数越多竞争越激烈

### 原因三：Scatter buffer 内存未对齐（辅因）

`IntegrateStressForElems` 和 `CalcHourglassControlForElems` 的 scatter buffer：

```cpp
std::vector<Real_t> fx_elem(numElem * 8);  // 无对齐保证
```

每个元素占 8 个 `double` = 64 字节 = 恰好一个 cache line。`std::vector` 默认分配器不保证 64 字节对齐，可能将相邻元素的 scatter 区域放在同一 cache line 上，导致不同线程写入时产生 **false sharing**，引发 cache 失效风暴。

## 三、优化方案与实施

### 阶段零：P-core 自动检测（零代码改动，立竿见影）

**目标文件**：[scripts/run.sh](scripts/run.sh)

在 macOS 下，`sysctl hw.perflevel0.physicalcpu` 可精确获取 P-core 数量。更新脚本，在未手动设置 `OMP_NUM_THREADS` 时自动默认为 P-core 数：

```bash
if [[ "$(uname -s)" == "Darwin" ]] && sysctl -n hw.perflevel0.physicalcpu &>/dev/null; then
    P_CORES=$(sysctl -n hw.perflevel0.physicalcpu)
    OMP_NUM_THREADS="${OMP_NUM_THREADS:-$P_CORES}"
    export OMP_NUM_THREADS
fi
```

同时新增 `scale` 模式，方便快速执行扩展性扫描：`./scripts/run.sh scale`。

### 阶段一：EOS 临时向量预分配（消除 malloc 竞争）

**目标文件**：[include/lulesh.h](include/lulesh.h)、[src/lulesh-eos.cc](src/lulesh-eos.cc)、[src/lulesh-init.cc](src/lulesh-init.cc)

**方案**：在 `ElemState` 结构体中添加 `EosTemps` 子结构，在 Domain 构造时按最大 region 尺寸一次性分配，跨 timestep 复用。Region 循环为串行，无数据竞争。

```cpp
// include/lulesh.h — ElemState 新增
struct EosTemps {
    std::vector<Real_t> e_old, delvc, p_old, q_old;
    std::vector<Real_t> compression, compHalfStep;
    std::vector<Real_t> qq_old, ql_old, work;
    std::vector<Real_t> p_new, e_new, q_new, bvc, pbvc;
    void reserve(Index_t n) { /* 14 个 resize(n) */ }
} m_eosTemps;
```

```cpp
// src/lulesh-init.cc — 构造函数末尾，CreateRegionIndexSets 之后
Index_t maxRegSize = 0;
for (Int_t r = 0; r < nr; ++r)
    if (regElemSize(r) > maxRegSize) maxRegSize = regElemSize(r);
m_elems.m_eosTemps.reserve(maxRegSize);
```

`EvalEOSForElems` 中原来的 14 行 `std::vector<Real_t>` 声明全部替换为：

```cpp
auto& t = domain.eosTemps();
Real_t* e_old_ptr = t.e_old.data();
// ... 其余指针直接取 t.xxx.data()
```

**效果**：将 ~154,000 次动态内存操作降低为构造时 1 次，彻底消除 malloc 全局锁竞争。

### 阶段二：Scatter buffer 64 字节对齐（消除 false sharing）

**目标文件**：[src/lulesh-stress.cc](src/lulesh-stress.cc)

将两处 scatter buffer（`IntegrateStressForElems` + `CalcHourglassControlForElems`）由 `std::vector` 改为 `std::aligned_alloc(64, ...)`：

```cpp
// 改前
std::vector<Real_t> fx_elem(numElem8);
Real_t* fx_elem_ptr = fx_elem.data();

// 改后
Real_t* fx_elem_ptr = static_cast<Real_t*>(
    std::aligned_alloc(64, numElem8 * sizeof(Real_t)));
// ... 使用后
std::free(fx_elem_ptr);
```

每个元素的 8 个分量 = 64 字节 = 恰好对齐到独立 cache line，**相邻元素的 scatter 写入保证不在同一 cache line 上**，彻底消除 false sharing。

### 阶段三：Region 循环展平（减少 barrier 数量）

**目标文件**：[src/lulesh-viscosity.cc](src/lulesh-viscosity.cc)、[src/lulesh-timestep.cc](src/lulesh-timestep.cc)

**黏性模块（Opt-10）**：`CalcMonotonicQForElems` 将 11 个 per-region `Kokkos::parallel_for` 展平为 1 个覆盖全部 `numElem` 的内核。关键前提：`monoq_limiter_mult`、`monoq_max_slope`、`qlc_monoq`、`qqc_monoq` 均为全局标量，与 region 无关，每个元素的计算体完全相同。

```cpp
// 改前：11 个 parallel_for，11 个 barrier
for (Index_t r = 0; r < numReg; ++r)
    Kokkos::parallel_for("...", regElemSize, [&](Index_t ielem) {
        Index_t i = domain.regElemlist(r, ielem); /* ... */ });

// 改后：1 个 parallel_for，1 个 barrier
Kokkos::parallel_for("CalcMonotonicQForElems", numElem,
    [&](Index_t i) { /* 完全相同的计算体，直接用 i */ });
```

**时间步约束（Opt-11）**：`CalcTimeConstraintsForElems` 将 11 个 per-region `parallel_reduce` 展平为 1 个覆盖全部 `numElem` 的双 `Kokkos::Min<Real_t>` 归约：

```cpp
// 改后：1 个 parallel_reduce，节省 10 个 barrier/step
Kokkos::parallel_reduce("CalcTimeConstraintsForElems", domain.numElem(),
    [&](Index_t indx, Real_t& lc, Real_t& lh) { /* Courant + Hydro */ },
    Kokkos::Min<Real_t>(dtc), Kokkos::Min<Real_t>(dth));
domain.dtcourant() = dtc;
domain.dthydro()   = dth;
```

两处合计每步节省 **20 个 barrier**。

## 五、技术决策与经验

### 1. `nowait` 语义的丢失是根本架构问题

原始 OpenMP 的 `#pragma omp for nowait` 允许 P-core 线程在完成后立即进入下一循环，无需等待慢核心。Kokkos `parallel_for` 的隐式全量 barrier 完全消除了这一优化机会。**在 P/E 异构硬件上，barrier 密度是首要性能杀手**，这正是本项目两轮内核融合能取得 2.15× 加速的根本原因。

### 2. Region 循环展平：正确性前提

展平成立的充分条件：**全部 domain 参数为全局标量，与 region 编号无关**。检查黏性和时间步模块后确认满足条件。EOS 模块因存在 per-region `rep` 循环（负载不均衡测试），展平逻辑复杂，暂不处理。

### 3. `aligned_alloc` vs `std::vector`

`std::aligned_alloc(64, n * sizeof(double))` 保证 64 字节对齐，而 `std::vector` 默认分配器仅保证 `alignof(double) = 8` 字节对齐。对于 scatter buffer，对齐后每个元素的 8 个分量恰好占据独立 cache line，是消除 false sharing 的充分条件。

### 4. P-core 数量的自动检测

`sysctl hw.perflevel0.physicalcpu` 在 macOS 13+ 上返回 P-core（performance level 0）的物理核心数，是目前不依赖第三方工具的最可靠方法。E-core 为 performance level 1，可通过 `hw.perflevel1.physicalcpu` 获取。
