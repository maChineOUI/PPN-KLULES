# Rapport hebdomadaire 2026-W15 | LULESH 2.0 Migration GPU Phase 4 : Migration de raw MPI vers la couche d'abstraction Kokkos-Comm

**Période** : 2026-04-06 ~ 2026-04-12
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU)
**Plateforme** : macOS Apple Silicon (validation locale) ; cible : Linux + NVIDIA GPU (backend CUDA)
**Référence de correction (cette semaine)** : GitHub officiel LLNL/LULESH tag `2.0.3`, commit `46c2a1d6`
**Conclusion** : Correction validée intégralement (C1–C11, 22 exécutions bilatérales concordantes) ; aucune dégradation systématique des performances

---

## Vue d'ensemble

Cette semaine correspond à la Phase 4 de la migration GPU de LULESH : migration de la couche MPI brute (établie la semaine précédente) vers l'interface d'abstraction **Kokkos-Comm**, afin de découpler le code métier de MPI. L'objectif principal est que le dépôt ne contienne qu'un seul fichier adaptatif MPI de taille réduite, tous les autres fichiers sources cessant d'appeler directement des fonctions `MPI_*`. Les travaux comprennent : (1) analyse des interfaces sources de Kokkos-Comm 0.2.0 ; (2) conception du plan de migration et évaluation des contraintes API ; (3) ajout d'une couche d'abstraction runtime et migration de l'ensemble des fichiers ; (4) deux cycles de validation interne et une validation comparative avec la référence officielle GitHub.

---

## I. Motivation et contraintes de conception

### 1.1 Pourquoi migrer vers Kokkos-Comm

L'implémentation raw MPI (W14) était fonctionnellement correcte, mais présentait les limitations suivantes :

- Les fichiers sources métier (`lulesh-comm.cc`, `lulesh-timestep.cc`, `lulesh_main.cc`, `lulesh-init.cc`) incluaient directement `<mpi.h>`, créant un couplage fort avec un runtime spécifique
- Les types `MPI_Request`, `MPI_Comm` polluaient la structure de domaine `DomainComm`
- Impossibilité d'exploiter l'abstraction des espaces d'exécution de Kokkos sur le même chemin de code

Kokkos-Comm fournit des interfaces de communication point-à-point et collective avec `Kokkos::View` comme type de données natif — la voie standard dans l'écosystème Kokkos pour atteindre l'indépendance vis-à-vis du backend de communication.

### 1.2 Contrainte d'interface et décision de conception clé

L'analyse du snapshot source Kokkos-Comm 0.2.0 (commit `2d1cd2c6`) révèle :

**Contrainte** : `KokkosComm::send` / `KokkosComm::recv` utilisent en interne un tag fixe `17`, **sans exposer de paramètre tag**.

**Problème** : l'implémentation originale distinguait les deux phases de communication halo par des tags différents (`MSG_COMM_SBN=1024`, `MSG_MONOQ=3072`). Si les deux phases partagent un même communicator avec un tag fixe, un rang rapide peut mélanger les messages de phases différentes.

**Solution** : dupliquer un communicator indépendant pour chaque phase halo :

```cpp
g_comm.sbnComm   = WorldComm().duplicate().value();
g_comm.monoqComm = WorldComm().duplicate().value();
```

La correspondance des messages MPI examine `(source, tag, communicator)` : des communicators distincts garantissent l'isolation absolue des phases, sans aucune constante de tag dans le code métier.

## II. Architecture de la migration

### 2.1 Structure finale en trois couches

| Couche | Fichier | Rôle |
|--------|---------|------|
| **A — Adaptateur MPI** | `src/lulesh-runtime-mpi.cc` | **Unique** fichier autorisé à appeler `MPI_*` dans le dépôt |
| **B — Interface runtime** | `include/lulesh-runtime.h` | Déclare `InitDistributedRuntime`, `BindWorldCommunicator`, `WorldComm()`, `DistributedRank()`, `DistributedSize()` |
| **C — Code métier** | Tous les autres fichiers | N'utilise que les interfaces de la couche B et `KokkosComm::*` |

### 2.2 Nouveaux fichiers

| Fichier | Rôle |
|---------|------|
| `src/lulesh-runtime-mpi.cc` | Initialisation/finalisation MPI ; `BindWorldCommunicator` encapsule `MPI_COMM_WORLD` dans `KokkosComm::Communicator<MpiSpace, DefaultExecSpace>` |
| `include/lulesh-runtime.h` | Déclarations de l'interface couche B ; alias de type `DistributedComm` |

### 2.3 Fichiers modifiés

| Fichier | Modification principale |
|---------|------------------------|
| `CMakeLists.txt` | `find_package(KokkosComm)` + fallback `KokkosComm_SOURCE_DIR` ; liaison `KokkosComm::KokkosComm` |
| `apps/lulesh_main.cc` | `MPI_Init/Finalize/Reduce` → `InitDistributedRuntime`, `BindWorldCommunicator`, `KokkosComm::Experimental::reduce` |
| `include/lulesh.h` | `DomainComm` : `MPI_Request[6]` → `KokkosComm::Request<MpiSpace>[6]` ; buffers `Real_t*` → `Kokkos::View<Real_t*, HostSpace>` |
| `include/lulesh-comm.h` | Ajout de la déclaration `CommTeardown()` |
| `src/lulesh-comm.cc` | **Suppression totale** de `<mpi.h>` ; `MPI_Isend/Irecv/Waitall` → `KokkosComm::send/recv/wait` |
| `src/lulesh-timestep.cc` | 2 × `MPI_Allreduce(MIN)` fusionnés en 1 × `KokkosComm::Experimental::allreduce(Min{})` |
| `src/lulesh-init.cc` | `MPI_Comm_rank()` → `DistributedRank()` |

## III. Détails d'implémentation

### 3.1 Ordre d'initialisation en deux phases

```cpp
InitDistributedRuntime(argc, argv);    // 1. MPI_Init_thread, rank, size
Kokkos::initialize(argc, argv);        // 2. Initialisation Kokkos (après MPI)
{
  BindWorldCommunicator(Kokkos::DefaultExecutionSpace{});  // 3. Liaison du communicator world
  // ...
  CommTeardown();                      // 4. Libération des communicators dupliqués (avant MPI_Finalize)
} // fin du scope Kokkos
Kokkos::finalize();                    // 5.
FinalizeDistributedRuntime();          // 6. MPI_Finalize
```

L'appel de `CommTeardown()` avant `MPI_Finalize` est une contrainte absolue : les destructeurs de `sbnComm`/`monoqComm` appellent `MPI_Comm_free`, ce qui doit précéder `MPI_Finalize`.

### 3.2 Nouvelle structure DomainComm

```cpp
struct DomainComm {
  using Comm = KokkosComm::Communicator<KokkosComm::MpiSpace, Exec>;
  using Req  = KokkosComm::Request<KokkosComm::MpiSpace>;

  std::optional<Comm> sbnComm;         // Dédié à la phase SBN
  std::optional<Comm> monoqComm;       // Dédié à la phase MONOQ

  Kokkos::View<Real_t*, Kokkos::HostSpace> sendBuf;
  Kokkos::View<Real_t*, Kokkos::HostSpace> recvBuf;

  std::array<Req, 6> recvReq;
  std::array<Req, 6> sendReq;
};
```

Les buffers `new[] Real_t` deviennent des `Kokkos::View<..., HostSpace>` : gestion automatique du cycle de vie avec `std::optional`, compatibilité directe avec `Kokkos::subview` pour l'extraction de tranches par face.

### 3.3 Migration du flux de communication halo

Exemple avec `CommSend` (symétrique pour `CommRecv`) :

```cpp
// Sélection du communicator de phase
auto& phaseComm = (msgType == MSG_COMM_SBN) ? *g_comm.sbnComm : *g_comm.monoqComm;

// Emballage des données (logique inchangée par rapport à la version MPI)
// ...

// Envoi : extraction d'une sous-vue, envoi non bloquant
auto slice = Kokkos::subview(g_comm.sendBuf, std::make_pair(offset, offset + count));
g_comm.sendReq[face] = KokkosComm::send(phaseComm, slice, dstRank);
```

`CommSBN`/`CommMonoQ` utilisent `KokkosComm::wait()` individuel plutôt que `wait_all` : dans Kokkos-Comm 0.2.0, `wait_all` ne remet pas les objets `Request` dans un état réutilisable, contrairement à `wait()` individuel.

### 3.4 Migration des communications collectives

Les 3 `MPI_Allreduce(MIN)` des contraintes temporelles sont fusionnés en 1 appel :

```cpp
Kokkos::View<Real_t*, Kokkos::HostSpace> send("dt_pair_send", 2);
Kokkos::View<Real_t*, Kokkos::HostSpace> recv("dt_pair_recv", 2);
send(0) = dtc;  send(1) = dth;
KokkosComm::Experimental::allreduce(WorldComm(), send, recv, KokkosComm::Min{}).wait();
domain.dtcourant() = recv(0);
domain.dthydro()   = recv(1);
```

Réduction du temps écoulé dans `main` :

```cpp
KokkosComm::Experimental::reduce(WorldComm(), elapsed_send, elapsed_recv, 0, KokkosComm::Max{}).wait();
```

## V. Synthèse des décisions techniques

### 5.1 Duplication de communicator en lieu et place des tags MPI

Décision architecturale centrale. L'interface point-à-point de Kokkos-Comm 0.2.0 n'expose pas de paramètre tag. La duplication de communicators (`sbnComm`/`monoqComm`) offre un isolation de phase via le troisième critère de matching MPI `(source, tag, communicator)`, sans aucune constante tag dans le code métier.

### 5.2 Initialisation en deux phases

`Communicator<MpiSpace, ExecSpace>` doit être lié à un espace d'exécution Kokkos déjà initialisé. La séquence `InitDistributedRuntime` → `Kokkos::initialize` → `BindWorldCommunicator` est une contrainte de cycle de vie non contournable.

### 5.3 Buffers DomainComm en HostSpace View

Le remplacement de `new[] Real_t` par `Kokkos::View<Real_t*, HostSpace>` apporte : (a) gestion automatique du cycle de vie avec `std::optional` ; (b) compatibilité directe avec `Kokkos::subview` pour alimenter `KokkosComm::send/recv` par tranches de face.

### 5.4 `wait()` individuel plutôt que `wait_all()`

`wait_all` dans Kokkos-Comm 0.2.0 copie les `MPI_Request` sous-jacents sans remettre les objets `Request` dans un état réutilisable propre. L'utilisation de `wait()` individuel par face offre un comportement plus déterministe et facilite le débogage.

## VI. Limitations connues et travaux futurs

1. **Cas P3 à reconduire** : la taille du problème était trop petite pour une mesure de temps fiable en configuration 8 ranks OMP=1
2. **Audit formel face-par-face non réalisé** : la validation actuelle reste de nature « forte validation empirique » sans traçage des compteurs par face de communication
3. **Pas de snapshot source raw-MPI reconstructible** : le HEAD du dépôt ne contient plus la version raw-MPI originale ; seule la comparaison avec le binaire existant est possible
4. **Validation GPU non encore réalisée** : l'exécution combinée avec le backend CUDA reste à valider sur un nœud Linux + NVIDIA GPU

## VIII. Comparaison de performance CPU+MPI avec la référence officielle GitHub

Suite à la validation de correction, une comparaison de performance initiale CPU+MPI (`OMP_NUM_THREADS=1`) a confirmé l'absence de dégradation systématique après la migration.

### 8.1 Méthode de test

- Référence officielle : `LLNL/LULESH` tag `2.0.3`, commit `46c2a1d6`, recompilé localement
- Version actuelle : `build-kokkos-comm/lulesh2.0`
- Paramètres communs : `--bind-to none -x OMP_NUM_THREADS=1 -x OMP_PROC_BIND=false`
- 3 exécutions par configuration, médiane du FOM (zone-updates/second)

| Cas | ranks | Paramètres | FOM médian référence | FOM médian actuel | Résultat |
|-----|------:|------------|--------------------:|------------------:|---------|
| M1 | 1 | `-i 20 -s 50` | 2387,4 | 2455,4 | +2,9 % |
| M2 | 8 | `-i 20 -s 30` | 8146,3 | 7811,0 | −3,8 % |
| M3 | 27 | `-i 20 -s 20` | 9677,3 | 10404,9 | +7,5 % |

Cohérence numérique : `Final Origin Energy` identique des deux côtés ; `MaxRelDiff` en `1e-13–1e-11` (arrondi double précision).

### 8.2 Conclusion

La version Kokkos-Comm offre des performances globalement équivalentes à LULESH 2.0 officiel sur CPU+MPI. Le léger recul de −3,8 % sur le cas M2 (8 ranks) correspond à un écart absolu de ~0,02 s et sera résorbé par les optimisations P1–P6 de la semaine suivante.
