# 周报 2026-W12 | LULESH 2.0 GPU 迁移 Phase 1：基础设施改造

**周期**：2026-03-16 ~ 2026-03-22
**项目**：LULESH 2.0 高性能计算代理应用（Kokkos 5 / GPU 迁移）
**平台**：macOS Apple Silicon（本地验证）；目标平台：Linux + NVIDIA GPU（CUDA 后端）
**正确性基准**：`OMP_PROC_BIND=close ./build/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## 本周工作概览

本周启动 LULESH 2.0 的 GPU 迁移工程（Phase 1），目标是在不改动计算逻辑的前提下，完成令代码能够在 NVIDIA GPU 上编译和运行所必需的全部基础设施改造。所有改动在 Apple M4 + OpenMP 后端上完成验证，保持正确性基准不变。

---

## 一、背景与目标

前两周的工作（W10~W11）将 LULESH 迁移至 Kokkos 5 OpenMP 后端，并通过内核融合取得了 2.15× 加速。然而该版本存在若干 CPU-only 假设，无法直接编译为 CUDA 目标：

| 问题 | 位置 | 影响 |
|------|------|------|
| lambda 以 `[&]` 捕获 `Domain&` 引用 | 全部 kernel 文件 | 设备端无法访问宿主栈地址 |
| 几何辅助函数无设备端标记 | `lulesh-geometry.cc` | 无法在 GPU 核函数中调用 |
| EOS 临时缓冲区为 `std::vector` | `lulesh.h` / `lulesh-eos.cc` | `std::vector` 不可在设备端访问 |
| `vnew` / `determ` 为 `std::vector` | `lulesh-integration.cc` / `lulesh-stress.cc` | 同上 |
| scatter buffer 使用 `std::aligned_alloc` | `lulesh-stress.cc` | 不可在设备端访问 |
| 三个嵌套结构体在 `Domain` 的 `private` 区 | `lulesh.h` | lambda 无法提取 View 句柄 |

Phase 1 解决前三列中的基础设施问题；Phase 2（下周）完成全部核函数的逐一迁移。

## 二、改动详情

### 2.1 几何辅助函数：添加 `KOKKOS_INLINE_FUNCTION`

**文件**：[include/lulesh-geometry.h](include/lulesh-geometry.h)、[src/lulesh-geometry.cc](src/lulesh-geometry.cc)

在 CUDA 编译模式下，设备核函数（`__global__`/`__device__`）只能调用被标记为 `__host__ __device__` 的函数。`KOKKOS_INLINE_FUNCTION` 宏在 CUDA 后端展开为 `inline __host__ __device__`，在 CPU 后端展开为 `inline`。

对以下函数在声明处添加 `KOKKOS_INLINE_FUNCTION`：

| 函数 | 作用 |
|------|------|
| `CalcElemShapeFunctionDerivatives` | 计算形函数导数（B 矩阵） |
| `CalcElemNodeNormals` | 计算单元节点法向量 |
| `CalcElemVolumeDerivative` | 体积对节点坐标的导数 |
| `CalcElemVolume`（两个重载） | 六面体单元体积 |
| `CalcElemCharacteristicLength` | 单元特征长度 |
| `SumElemFaceNormal`（内部 static） | 面法向量累加 |
| `VoluDer`（内部 static） | 体积偏导辅助 |
| `AreaFace`（内部 static） | 面面积计算 |

`CollectDomainNodesToElemNodes` 接受 `Domain&`（宿主对象），不标记，保留为 host-only 函数，后续在核函数中直接内联替代。

同时将 `std::max` → `Kokkos::max`，`std::sqrt` → `Kokkos::sqrt`，以使这些函数体在 GPU 上合法。

### 2.2 `lulesh.h`：结构体公开化 + `EosTemps` View 化

**文件**：[include/lulesh.h](include/lulesh.h)

**结构体公开化**：将 `NodeArrays m_nodes`、`ElemConnectivity m_conn`、`ElemState m_elems` 三个嵌套结构体从 `Domain` 的 `private` 区移至 `public` 区。这是必要前提——`KOKKOS_LAMBDA`（`[=]` 捕获）只能从调用方的作用域提取 View 句柄，而核函数调用方（各 `.cc` 文件中的函数）需要能直接访问 `domain.m_nodes.m_x` 等成员。

**`EosTemps` View 化**：将 `EosTemps` 结构体中的 14 个 `std::vector<Real_t>` 字段全部替换为 `Kokkos::View<Real_t*>`，并更新 `reserve()` 方法：

```cpp
// 改前
struct EosTemps {
    std::vector<Real_t> e_old, delvc, p_old, q_old;
    // ... 共 14 个
    void reserve(Index_t n) { e_old.resize(n); /* ... */ }
};

// 改后
struct EosTemps {
    Kokkos::View<Real_t*> e_old, delvc, p_old, q_old;
    Kokkos::View<Real_t*> compression, compHalfStep;
    Kokkos::View<Real_t*> qq_old, ql_old, work;
    Kokkos::View<Real_t*> p_new, e_new, q_new, bvc, pbvc;
    void reserve(Index_t n) {
        e_old = Kokkos::View<Real_t*>("eos_e_old", n);
        // ... 全部 14 个字段
    }
};
```

`Kokkos::View` 的内存默认分配在 `DefaultMemorySpace`：OpenMP 后端为 `HostSpace`，CUDA 后端为 `CudaSpace`，自动适配目标设备。

### 2.3 `vnew` / `determ`：临时数组 View 化

**文件**：[src/lulesh-integration.cc](src/lulesh-integration.cc)、[src/lulesh-stress.cc](src/lulesh-stress.cc)

`vnew`（单元相对体积）和 `determ`（体积行列式）是跨函数传递的每步临时数组，必须在设备可访问的内存中分配：

```cpp
// 改前
std::vector<Real_t> vnew(numElem);
// ... 传递 vnew.data() 指针

// 改后
Kokkos::View<Real_t*> vnew("vnew", numElem);
// ... 直接传递 View
```

相关函数签名同步更新（`lulesh-kinematics.h/.cc`、`lulesh-viscosity.h/.cc`、`lulesh-eos.h/.cc`），将 `Real_t*` 参数改为 `Kokkos::View<Real_t*>`。

### 2.4 CMakeLists.txt：CUDA 后端检测

**文件**：[CMakeLists.txt](CMakeLists.txt)

添加 `kokkos_check` 块，当 Kokkos 安装时启用了 CUDA 后端，自动将所有含 `KOKKOS_LAMBDA` 的源文件标记为 CUDA 语言，使 `nvcc_wrapper` 正确处理设备端代码：

```cmake
kokkos_check(DEVICES "CUDA" RETURN_VALUE HAVE_CUDA)
if(HAVE_CUDA)
    message(STATUS "Kokkos CUDA backend detected — marking kernel sources as CUDA")
    set_source_files_properties(
        src/lulesh-kinematics.cc
        src/lulesh-stress.cc
        src/lulesh-viscosity.cc
        src/lulesh-eos.cc
        src/lulesh-nodal.cc
        src/lulesh-timestep.cc
        src/lulesh-geometry.cc
        src/lulesh-integration.cc
        apps/lulesh_main.cc
        PROPERTIES LANGUAGE CUDA
    )
endif()
```

Linux + NVIDIA GPU 的完整构建命令：
```bash
cmake -S . -B build-cuda \
      -DCMAKE_CXX_COMPILER=/path/to/kokkos/bin/nvcc_wrapper \
      -DKokkos_ENABLE_CUDA=ON \
      -DKokkos_ENABLE_CUDA_LAMBDA=ON \
      -DKokkos_ARCH_AMPERE80=ON \
      -DCMAKE_BUILD_TYPE=Release
```

## 四、技术决策

### 1. 为什么将结构体从 `private` 移至 `public`？

`KOKKOS_LAMBDA` 展开为 `[=]`（值捕获），闭包内无法捕获 `Domain&` 本身（宿主指针无法在设备端解引用）。正确做法是在 lambda 外提取所需 `Kokkos::View` 为局部变量，再由 `[=]` 捕获——这需要调用方能访问 `domain.m_nodes.m_x` 等成员。将结构体公开是最小侵入性的方案。

### 2. 为什么 `EosTemps` 的字段必须是 `Kokkos::View`？

`std::vector` 的内部指针指向宿主堆内存。当 `KOKKOS_LAMBDA` 以值捕获 `Kokkos::View<Real_t*>` 时，只拷贝了 View 的元数据（指针+extent），设备端可以通过该元数据访问对应的设备内存。而 `std::vector::data()` 返回的宿主指针在 GPU 核函数中无效。

### 3. `vnew` / `determ` 改为 View 后的接口变化

函数参数类型从 `Real_t*`（裸指针）改为 `Kokkos::View<Real_t*>`，访问方式从 `vnew[i]` 改为 `vnew(i)`（Kokkos::View 重载了 `operator()`，不重载 `operator[]`）。
