# Rapport hebdomadaire 2026-W12 | LULESH 2.0 Migration GPU Phase 1 : Infrastructure

**Période** : 2026-03-16 ~ 2026-03-22
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU)
**Plateforme** : macOS Apple Silicon (validation locale) ; cible : Linux + NVIDIA GPU (backend CUDA)
**Référence de correction** : `OMP_PROC_BIND=close ./build/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## Vue d'ensemble

Cette semaine lance la migration GPU de LULESH 2.0 (Phase 1). L'objectif est de réaliser toutes les modifications d'infrastructure nécessaires pour que le code puisse être compilé et exécuté sur un GPU NVIDIA, sans toucher à la logique de calcul. Toutes les modifications sont validées sur Apple M4 + backend OpenMP, la référence de correction reste inchangée.

---

## I. Contexte et objectifs

Les travaux des semaines W10–W11 ont migré LULESH vers Kokkos 5 (backend OpenMP) et obtenu une accélération de 2,15×. Cette version comporte cependant plusieurs hypothèses CPU-only qui empêchent la compilation en cible CUDA :

| Problème | Emplacement | Impact |
|----------|-------------|--------|
| Lambda avec capture `[&]` de `Domain&` | Tous les fichiers noyaux | L'adresse de pile hôte est inaccessible côté device |
| Fonctions géométriques sans marquage device | `lulesh-geometry.cc` | Non appelables dans les noyaux GPU |
| Buffers temporaires EOS de type `std::vector` | `lulesh.h` / `lulesh-eos.cc` | `std::vector` non accessible côté device |
| `vnew` / `determ` de type `std::vector` | `lulesh-integration.cc` / `lulesh-stress.cc` | Idem |
| Buffers scatter via `std::aligned_alloc` | `lulesh-stress.cc` | Non accessible côté device |
| Trois structures imbriquées dans la section `private` de `Domain` | `lulesh.h` | Impossible d'extraire les handles `View` |

La Phase 1 traite les problèmes d'infrastructure ; la Phase 2 (semaine prochaine) migre les noyaux un par un.

## II. Modifications détaillées

### 2.1 Fonctions géométriques : ajout de `KOKKOS_INLINE_FUNCTION`

**Fichiers** : [include/lulesh-geometry.h](include/lulesh-geometry.h), [src/lulesh-geometry.cc](src/lulesh-geometry.cc)

En mode de compilation CUDA, les noyaux device ne peuvent appeler que des fonctions marquées `__host__ __device__`. La macro `KOKKOS_INLINE_FUNCTION` se développe en `inline __host__ __device__` pour CUDA et en `inline` pour les backends CPU.

Les fonctions suivantes reçoivent `KOKKOS_INLINE_FUNCTION` dans leur déclaration :

| Fonction | Rôle |
|----------|------|
| `CalcElemShapeFunctionDerivatives` | Calcul des dérivées des fonctions de forme (matrice B) |
| `CalcElemNodeNormals` | Normales aux nœuds d'un élément |
| `CalcElemVolumeDerivative` | Dérivée du volume par rapport aux coordonnées nodales |
| `CalcElemVolume` (2 surcharges) | Volume d'un hexaèdre |
| `CalcElemCharacteristicLength` | Longueur caractéristique de l'élément |
| `SumElemFaceNormal` (static interne) | Accumulation des normales de face |
| `VoluDer` (static interne) | Dérivée partielle de volume |
| `AreaFace` (static interne) | Calcul de l'aire d'une face |

`CollectDomainNodesToElemNodes` reçoit `Domain&` (objet hôte) et reste une fonction host-only ; elle sera remplacée par une boucle inline aux points d'appel dans les noyaux.

`std::max` → `Kokkos::max`, `std::sqrt` → `Kokkos::sqrt` pour que les corps de ces fonctions soient valides sur GPU.

### 2.2 `lulesh.h` : exposition des structures + View-ification d'`EosTemps`

**Fichier** : [include/lulesh.h](include/lulesh.h)

**Exposition des structures** : les trois structures imbriquées `NodeArrays m_nodes`, `ElemConnectivity m_conn`, `ElemState m_elems` sont déplacées de la section `private` vers la section `public` de `Domain`. C'est un prérequis nécessaire : `KOKKOS_LAMBDA` (capture `[=]`) ne peut pas capturer `Domain&` directement, mais peut capturer des `Kokkos::View` extraits comme variables locales — ce qui suppose que le code appelant puisse accéder à `domain.m_nodes.m_x`, etc.

**View-ification d'`EosTemps`** : les 14 champs `std::vector<Real_t>` de la structure `EosTemps` sont remplacés par `Kokkos::View<Real_t*>`, et la méthode `reserve()` est mise à jour :

```cpp
// Avant
struct EosTemps {
    std::vector<Real_t> e_old, delvc, p_old, q_old;
    // ... 14 au total
    void reserve(Index_t n) { e_old.resize(n); /* ... */ }
};

// Après
struct EosTemps {
    Kokkos::View<Real_t*> e_old, delvc, p_old, q_old;
    Kokkos::View<Real_t*> compression, compHalfStep;
    Kokkos::View<Real_t*> qq_old, ql_old, work;
    Kokkos::View<Real_t*> p_new, e_new, q_new, bvc, pbvc;
    void reserve(Index_t n) {
        e_old = Kokkos::View<Real_t*>("eos_e_old", n);
        // ... 14 champs
    }
};
```

La mémoire allouée par `Kokkos::View` correspond au `DefaultMemorySpace` : `HostSpace` pour OpenMP, `CudaSpace` pour CUDA — adaptation automatique à la cible.

### 2.3 `vnew` / `determ` : View-ification des tableaux temporaires

**Fichiers** : [src/lulesh-integration.cc](src/lulesh-integration.cc), [src/lulesh-stress.cc](src/lulesh-stress.cc)

`vnew` (volume relatif des éléments) et `determ` (déterminant de volume) sont des tableaux temporaires par pas de temps transmis entre fonctions. Ils doivent résider dans une mémoire accessible par le device :

```cpp
// Avant
std::vector<Real_t> vnew(numElem);

// Après
Kokkos::View<Real_t*> vnew("vnew", numElem);
```

Les signatures des fonctions concernées sont mises à jour en conséquence (`lulesh-kinematics.h/.cc`, `lulesh-viscosity.h/.cc`, `lulesh-eos.h/.cc`) : paramètre `Real_t*` → `Kokkos::View<Real_t*>`.

### 2.4 CMakeLists.txt : détection du backend CUDA

**Fichier** : [CMakeLists.txt](CMakeLists.txt)

Ajout d'un bloc `kokkos_check` : si Kokkos a été installé avec le backend CUDA activé, tous les fichiers sources contenant des `KOKKOS_LAMBDA` sont automatiquement marqués comme CUDA afin que `nvcc_wrapper` traite correctement le code device :

```cmake
kokkos_check(DEVICES "CUDA" RETURN_VALUE HAVE_CUDA)
if(HAVE_CUDA)
    message(STATUS "Kokkos CUDA backend detected — marking kernel sources as CUDA")
    set_source_files_properties(
        src/lulesh-kinematics.cc  src/lulesh-stress.cc
        src/lulesh-viscosity.cc   src/lulesh-eos.cc
        src/lulesh-nodal.cc       src/lulesh-timestep.cc
        src/lulesh-geometry.cc    src/lulesh-integration.cc
        apps/lulesh_main.cc
        PROPERTIES LANGUAGE CUDA
    )
endif()
```

Commande de construction complète pour Linux + NVIDIA GPU :
```bash
cmake -S . -B build-cuda \
      -DCMAKE_CXX_COMPILER=/path/to/kokkos/bin/nvcc_wrapper \
      -DKokkos_ENABLE_CUDA=ON \
      -DKokkos_ENABLE_CUDA_LAMBDA=ON \
      -DKokkos_ARCH_AMPERE80=ON \
      -DCMAKE_BUILD_TYPE=Release
```

## IV. Décisions techniques

### 1. Pourquoi rendre les structures publiques ?

`KOKKOS_LAMBDA` se développe en `[=]` (capture par valeur). La fermeture ne peut pas capturer `Domain&` (pointeur hôte inaccessible côté device). La bonne pratique consiste à extraire les `Kokkos::View` nécessaires en variables locales avant le lambda, puis les capturer par `[=]`. Cela nécessite que le code appelant puisse accéder directement à `domain.m_nodes.m_x`, etc. Rendre les structures publiques est la modification la moins invasive.

### 2. Pourquoi les champs d'`EosTemps` doivent être des `Kokkos::View` ?

Le pointeur interne d'un `std::vector` pointe vers la mémoire heap de l'hôte. Lors d'une capture `[=]` d'un `Kokkos::View<Real_t*>`, seules les métadonnées (pointeur + extent) sont copiées ; le noyau device y accède ensuite via la mémoire device associée. Un pointeur `std::vector::data()` est invalide dans un noyau GPU.

### 3. Changement d'interface pour `vnew` / `determ`

Le type du paramètre passe de `Real_t*` (pointeur brut) à `Kokkos::View<Real_t*>`. L'accès passe de `vnew[i]` à `vnew(i)` (`Kokkos::View` surcharge `operator()`, pas `operator[]`).
