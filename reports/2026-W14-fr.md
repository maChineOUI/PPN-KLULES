# Rapport hebdomadaire 2026-W14~W15 | LULESH 2.0 Optimisation GPU P1 + P2

**Période** : 2026-03-30 ~ 2026-04-12
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU, branche `gpu-port`)
**Plateforme** : macOS Apple Silicon (validation locale OpenMP) ; cible : Linux + RTX 4070 Laptop GPU (backend CUDA)
**Référence de correction** : `OMP_PROC_BIND=close ./build/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## Vue d'ensemble

Rapport couvrant deux semaines de travail et deux optimisations GPU :

- **P1** (W14) : Pré-allocation de toutes les `Kokkos::View` transitoires dans le constructeur de `Domain`, éliminant ~28 `cudaMalloc + cudaFree` par pas de temps.
- **P2** (W15) : Suite au test GPU de P1, le profilage Nsight Compute a révélé deux nouveaux goulots — pression sur les registres (occupation SM 25 %) et bande passante DRAM du pattern scatter-gather. P2 comprend une première implémentation, un test GPU, une analyse des échecs et une correction.

---

### 1.1 Données de profilage (Nsight Systems, `-s 30 -i 10`)

| `cudaMalloc` + `cudaFree` | ~75 % | ~337 |

**Conclusion** : l'overhead d'allocation mémoire dépasse de loin le calcul effectif.

## II. P1 — Implémentation

### 2.1 Principe

Toutes les `View` transitoires sont promues en membres de `Domain`, allouées une seule fois dans le constructeur et réutilisées à chaque pas de temps.

### 2.2 Modifications de `include/lulesh.h`

**① `ElemConnectivity` — listes d'indices de région côté device**

```cpp
struct ElemConnectivity {
    std::vector<std::vector<Index_t>> m_regElemlist;     // hôte (conservé)
    std::vector<Kokkos::View<Index_t*>> m_regElemlist_d; // ← device (P1)
} m_conn;
```

**② `ElemState` — `ScratchViews`**

```cpp
struct ScratchViews {
    Kokkos::View<Real_t*> m_vnew;    // volume relatif (numElem)
    Kokkos::View<Real_t*> m_determ;  // déterminant Jacobien (numElem)
    void reserve(Index_t numElem) { /* allocation unique */ }
} m_scratch;
```

**③ 4 méthodes Allocate/Deallocate converties en no-ops**

```cpp
void AllocateGradients(Int_t, Int_t) {}
void DeallocateGradients() {}
void AllocateStrains(Int_t) {}
void DeallocateStrains() {}
```

### 2.3 Modifications des modules de calcul

| Fichier | Avant | Après |
|---------|-------|-------|
| `lulesh-eos.cc` | `deep_copy` de la liste de région par pas | `domain.regElemlistDevice(r)` (upload unique) |
| `lulesh-integration.cc` | `Kokkos::View<Real_t*> vnew("vnew", numElem)` | `auto& vnew = domain.m_elems.m_scratch.m_vnew` |
| `lulesh-stress.cc` (IntegrateStress) | 3 Views locales `fx/fy/fz_elem` | Views scratch |
| `lulesh-stress.cc` (CalcHourglass) | 3 Views locales `hg_fx/fy/fz` | Views scratch |
| `lulesh-stress.cc` (CalcVolumeForce) | `determ` locale | `domain.m_elems.m_scratch.m_determ` |

## IV. P2 — Résultats du test GPU et analyse des échecs

### 4.1 FOM initiaux (GPU, RTX 4070 Laptop)

| Taille | P1 (base) | P2 initial | Variation |
|--------|-----------|------------|-----------|
| `-s 30` | 12 687 z/s | 10 561 z/s | **−17 %** |
| `-s 45` | 21 341 z/s | 22 848 z/s | **+7 %** |

Résultats contradictoires — la première implémentation P2 est défectueuse.

### 4.2 Métriques ncu — kernels principaux

| Kernel | Regs/thread | Occupation SM | Throughput compute |
|--------|-------------|---------------|--------------------|
| `CalcHourglassControlForElems` | 168 | **25 %** | 88 % |
| `CalcKinematicsAndLagrange` | 144 | **25 %** | 85 % |
| `CalcMonotonicQGradientsForElems` | 118 | **33 %** | — |
| `IntegrateStressForElems` | — | — | 81 % |

`LaunchBounds<256,2>` n'a eu **aucun effet** ; l'étape `contribute()` atteint **93 % de bande passante DRAM**.

### 4.3 Échec de P2-A : contrainte LaunchBounds trop permissive

La contrainte `LaunchBounds<maxT, minB>` est : `minB × threadsPerBlock × R ≤ 65536`

```
LaunchBounds<256,2> : 2 × 128 × R ≤ 65536  →  R ≤ 256  (168 < 256 → aucun effet)
LaunchBounds<128,4> : 4 × 128 × R ≤ 65536  →  R ≤ 128  (168 > 128 → spillage déclenché)
```

### 4.4 Problème de P2-B : mode ScatterView ambigu

Interprétation initiale : `create_scatter_view()` sélectionne `ScatterDuplicated + ScatterNonAtomic` (copies privées par thread + réduction), l'étape `contribute()` devient le nouveau goulot DRAM et explique la régression de −17 % à `s = 30`.

> **Réserve** : sur sm_89, les atomiques globales contournent L1 et transitent par L2. `l1tex__...atom = 0` est **attendu même si des atomiques sont utilisées**. Le compteur pertinent est `l2__global_atomic_requests.sum` (non mesuré). L'hypothèse reste à confirmer.

### 4.5 Nouvelle cible identifiée : `CalcMonotonicQGradientsForElems`

118 registres/thread, 33 % d'occupation SM — non ciblé initialement, intégré en P2-D.

## V. P2 — Corrections implémentées

### 5.1 Correction P2-A : `LaunchBounds<128,4>` (trois sites)

```cpp
// src/lulesh-stress.cc — CalcHourglassControlForElems
using hg_policy_t  = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;

// src/lulesh-kinematics.cc — CalcKinematicsAndLagrange
using kin_policy_t = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;

// src/lulesh-viscosity.cc — CalcMonotonicQGradientsForElems (P2-D)
using mono_policy_t = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;
```

### 5.2 Correction P2-B : `ScatterNonDuplicated + ScatterAtomic` explicite

```cpp
using node_sv_t = Kokkos::Experimental::ScatterView<Real_t*,
    typename decltype(fx_v)::array_layout,
    typename decltype(fx_v)::execution_space,
    Kokkos::Experimental::ScatterSum,
    Kokkos::Experimental::ScatterNonDuplicated,
    Kokkos::Experimental::ScatterAtomic>;
node_sv_t fx_scatter(fx_v);
```

Avec `ScatterNonDuplicated`, l'appel `contribute()` devient un no-op. Les deux sites modifiés : `IntegrateStressForElems` et `CalcHourglassControlForElems`.

## VI. Points techniques clés et incertitudes

### 6.1 Sémantique de copie de `Kokkos::View` (P1)

`auto& vnew = domain.m_elems.m_scratch.m_vnew` est une référence — aucune allocation supplémentaire. Seules les métadonnées sont copiées lors du passage par valeur ; la mémoire device reste partagée.

### 6.2 `allElem` inclut les cellules fantômes (P1)

`allElem = numElem + 6 × faces fantômes`, nécessaire pour les Views de gradient de vitesse indexées au-delà des frontières.

### 6.3 LaunchBounds est un hint, pas une contrainte absolue (P2)

Le spillage de registres induit un trafic L1 supplémentaire, potentiellement coûteux dans un kernel compute-bound (88 % pour CalcHourglass). L'effet net ne peut être évalué que par mesure.

### 6.4 Modifications simultanées — validation difficile à isoler (P2)

Trois LaunchBounds + deux ScatterView modifiés ensemble. En cas de résultat inattendu, des tests A/B isolés seront nécessaires.
