**Période** : 2026-03-30 ~ 2026-04-05
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU)
**Plateforme** : macOS Apple Silicon (validation locale) ; cible : Linux + NVIDIA GPU (backend CUDA)

## Vue d'ensemble

Cette semaine correspond à la Phase 3 de la migration GPU de LULESH : ajout d'une couche de communication MPI multi-processus au-dessus de l'accélération GPU Kokkos, en suivant la même stratégie de décomposition de domaine et les mêmes patrons de communication que l'implémentation de référence LULESH 2.0 originale. Les travaux comprennent : (1) analyse de l'implémentation MPI originale de LULESH 2.0 ; (2) conception et implémentation du module de communication `lulesh-comm.cc` ; (3) insertion des appels MPI aux points critiques du pipeline de calcul ; (4) correction de plusieurs bogues à l'exécution et validation de la correction en mono- et multi-processus.

## I. Analyse de référence : MPI dans LULESH 2.0 original

Avant toute implémentation, l'analyse systématique du dépôt LLNL/LULESH a établi les décisions de conception servant de référence :

### 1.1 Patron de communication

LULESH 2.0 utilise une **décomposition de domaine 3D cartésienne** — le nombre de processus doit être un cube parfait (1, 8, 27…). Chaque processus communique avec jusqu'à 26 voisins (6 faces + 12 arêtes + 8 coins). La présente implémentation se limite aux **6 faces uniquement** : la connectivité des éléments du GPU port (`lxim/lxip/letam/letap/lzetam/lzetap`) ne référence qu'une seule couche de cellules fantômes, sans arêtes ni coins.

### 1.2 Types de messages

| Type | Tag | Données | Mode de déballage |
|------|-----|---------|-------------------|
| `MSG_COMM_SBN` | 1024 | Forces nodales (fx/fy/fz) | **scatter-add** (accumulation sur les nœuds frontière partagés) |
| `MSG_MONOQ` | 3072 | Gradients de vitesse (delv_xi/eta/zeta) | **écrasement direct** (écriture dans les slots fantômes pré-alloués) |

### 1.3 Stratégie non bloquante

Conformément à la référence : `MPI_Irecv` + `MPI_Isend` + `MPI_Wait/Waitall`. Les réceptions sont affichées en premier (`CommRecv`), puis les envois (`CommSend`), puis l'attente et le déballage (`CommSBN` / `CommMonoQ`).

### 1.4 Réduction globale du pas de temps

À chaque pas de temps, les contraintes locales de Courant et hydro sont fusionnées en minimum global par `MPI_Allreduce(MPI_MIN)`, garantissant un `deltatime` cohérent entre tous les processus.

## III. Implémentation de lulesh-comm.cc

### 3.1 Structure globale DomainComm

Pour éviter de polluer la définition de `Domain` avec des types MPI lorsque `USE_MPI=0`, l'état de communication est extrait dans une structure indépendante, déclarée à la fin de `lulesh.h` :

```cpp
struct DomainComm {
    Real_t      *sendBuf ;
    Real_t      *recvBuf ;
    MPI_Request  recvRequest[6] ;
    MPI_Request  sendRequest[6] ;
} ;
extern DomainComm g_comm ;
```

La taille des tampons est calculée sur l'aire nodale `(nx+1)²` — toujours supérieure à l'aire élémentaire — pour couvrir les deux types d'échanges.

### 3.2 Numérotation des faces et voisins

Les 6 faces sont numérotées dans un ordre fixe, correspondant aux décalages `(dc, dr, dp)` dans la grille cartésienne 3D :

| N° | Face | Décalage (dc,dr,dp) | Taille |
|----|------|---------------------|--------|
| 0 | planeMin (zeta-) | (0, 0, -1) | dx×dy |
| 1 | planeMax (zeta+) | (0, 0, +1) | dx×dy |
| 2 | rowMin (eta-)   | (0, -1, 0) | dx×dz |
| 3 | rowMax (eta+)   | (0, +1, 0) | dx×dz |
| 4 | colMin (xi-)    | (-1, 0, 0) | dy×dz |
| 5 | colMax (xi+)    | (+1, 0, 0) | dy×dz |

Rang du voisin : `plane×tp² + row×tp + col`, avec `tp = ∛numRanks`.

### 3.3 Logique de conditionnement dans CommSend

Les paramètres `dx/dy/dz` servent à la fois de bornes de boucle et de pas d'indexation (éléments : `nx` ; nœuds : `nx+1`), évitant toute duplication de code :

```cpp
// face=0 : plan planeMin, envoi de la tranche k=0
for (fld in fields)
    for j in [0, dy): for i in [0, dx):
        buf[idx++] = fieldData[fld][j*dx + i];

// face=1 : plan planeMax, envoi de la tranche k=dz-1
for (fld in fields)
    for j in [0, dy): for i in [0, dx):
        buf[idx++] = fieldData[fld][(dz-1)*dy*dx + j*dx + i];
```

### 3.4 Déballage CommSBN (scatter-add)

Les forces nodales sur les frontières inter-processus sont calculées partiellement par plusieurs processus ; la contribution reçue doit être **accumulée** :

```cpp
// face=0 : réception du voisin zeta-, accumulation sur le plan k=0
for (fld in fields)
    for j in [0, EN): for i in [0, EN):
        fieldData[fld][j*EN + i] += recvBuf[idx++];  // accumulation
```

### 3.5 Déballage CommMonoQ (écrasement des cellules fantômes)

Les slots fantômes sont pré-alloués par `SetupBoundaryConditions` au-delà de `numElem` ; les données reçues y sont écrites directement :

```cpp
for (e in [0, faceSize)):
    dxi_h(ghostBase[face] + e)   = buf[3*e    ];
    deta_h(ghostBase[face] + e)  = buf[3*e + 1];
    dzeta_h(ghostBase[face] + e) = buf[3*e + 2];
Kokkos::deep_copy(domain.m_elems.m_delv_xi, dxi_h);
```

## IV. Flux de données GPU-MPI

Chaque point de communication suit le même schéma en trois étapes :

```
Calcul GPU → deep_copy(GPU→hôte) → Communication MPI → deep_copy(hôte→GPU) → Calcul GPU suivant
```

**Point 1** (dans `LagrangeNodal`) :

```
CalcForceForNodes()          ← GPU calcule les forces nodales
  deep_copy fx/fy/fz → miroir hôte
  CommRecv(MSG_COMM_SBN, dx=EN, dy=EN, dz=EN)
  CommSend(MSG_COMM_SBN, champs=[fx,fy,fz])
  CommSBN()                  ← Wait + scatter-add
  deep_copy fx/fy/fz → device
CalcAccelerationForNodes()   ← GPU utilise les forces mises à jour
```

**Point 2** (dans `CalcQForElems`) :

```
CalcMonotonicQGradientsForElems()  ← GPU calcule les gradients
  deep_copy delv_xi/eta/zeta → hôte
  CommRecv(MSG_MONOQ, dx=nx, dy=ny, dz=nz)
  CommSend(MSG_MONOQ, champs=[dxi,deta,dzeta])
  CommMonoQ()               ← Wait + écriture slots fantômes + deep_copy → device
CalcMonotonicQForElems()    ← GPU lit le tableau complet avec fantômes
```

**Point 3** (dans `TimeIncrement`) :

```
MPI_Allreduce(&gnewdt, &newdt, MPI_MIN)  ← pas de temps global minimum
```

## V. Débogage et corrections

### 5.1 Erreur d'accès aux membres privés

**Symptôme** : première compilation — `'m_colLoc' is a private member of 'Domain'`, 20 erreurs d'accès.

**Cause** : les tampons MPI et les handles `MPI_Request[6]` avaient été placés dans la section `private` de `Domain` ; `lulesh-comm.cc` ne peut pas y accéder en tant qu'unité de traduction externe ; les accesseurs `m_rowMin/Max` manquaient également.

**Correction** : extraction de l'état MPI dans `DomainComm g_comm` (contourne entièrement le contrôle d'accès) ; ajout de 6 accesseurs publics dans `lulesh.h`.

### 5.2 Segfault sur MPI_Waitall — requêtes sendRequest non initialisées

**Symptôme** : crash en exécution mono-processus (sans voisin réel) dans `MPI_Waitall`, adresse `0x38`.

**Cause** : `CommSend` ignore les faces sans voisin, laissant `sendRequest[face]` non initialisé ; `MPI_Waitall` lit une valeur parasite.

**Correction** : pré-initialisation systématique avant la boucle d'envoi :

```cpp
for (int face = 0; face < 6; ++face)
    g_comm.sendRequest[face] = MPI_REQUEST_NULL;
```

### 5.3 Dépassement de tampon — taille calculée sur les éléments, non les nœuds

**Symptôme** : `CommSetup` allouait les tampons selon l'aire élémentaire (`nx×ny`), mais l'échange de forces nodales utilise l'aire nodale (`(nx+1)²`). Débordement de tampon corrompant la mémoire adjacente, provoquant un crash dans le noyau Kokkos OpenMP `IntegrateStressForElems` (Segfault, adresse `0x0`) en multi-processus.

**Correction** : taille des tampons calculée sur l'aire nodale :

```cpp
Index_t EN = domain.sizeX() + 1;
Index_t bufSize = 3 * 6 * EN * EN;  // aire nodale > aire élémentaire
```

## VII. Décisions techniques

### 1. DomainComm global plutôt que membre de Domain

Extraction de l'état MPI dans une structure globale : (a) évite d'inclure les en-têtes MPI dans `lulesh.h` lorsque `USE_MPI=0` ; (b) `Domain` contient déjà de nombreux membres GPU publics — l'état MPI relève d'une couche de communication d'exécution, sa séparation respecte le principe de responsabilité unique.

### 2. Communication 6 faces uniquement

LULESH 2.0 original implémente 26 voisins (faces + arêtes + coins). Dans le GPU port, la connectivité `lxim/lxip` etc. ne pointe que vers des cellules fantômes de face ; arêtes et coins ne sont jamais accédés. Les 6 faces sont numériquement suffisantes et réduisent considérablement la complexité d'implémentation.

### 3. Paramètres dx/dy/dz unifiés pour éléments et nœuds

`CommSend` utilise `dx/dy/dz` à la fois comme bornes de boucle et comme pas d'indexation. Pour l'échange de forces : `dx=dy=dz=nx+1` ; pour les gradients : `dx=dy=dz=nx`. Les deux cas partagent le même code de conditionnement, sans duplication.

### 4. Stratégie GPU-MPI conservative : deep_copy explicite

La stratégie actuelle effectue des `deep_copy` explicites (GPU→hôte, hôte→GPU) à chaque point de communication. Elle est correcte en l'absence de MPI CUDA-aware et préserve la structure pour une optimisation ultérieure (transmission directe de pointeurs device, ou recouvrement communication/calcul).
