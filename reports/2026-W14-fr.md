# Rapport hebdomadaire 2026-W14 | LULESH 2.0 Optimisation GPU P1 : Élimination de tous les cudaMalloc/cudaFree par pas de temps

**Période** : 2026-03-30 ~ 2026-04-05
**Projet** : Application proxy HPC LULESH 2.0 (Kokkos 5 / migration GPU, branche `gpu-port`)
**Plateforme** : macOS Apple Silicon (validation locale OpenMP) ; cible : Linux + RTX 4070 Laptop GPU (backend CUDA)
**Référence de correction** : `OMP_PROC_BIND=close ./build/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## Vue d'ensemble

Cette semaine a été consacrée à l'**optimisation P1** : pré-allocation de toutes les `Kokkos::View` transitoires dans le constructeur de `Domain`, afin d'éliminer les ~28 appels `cudaMalloc + cudaFree` par pas de temps (dont l'allocation dynamique de `regElemList` à chaque appel d'`EvalEOSForElems`). Le profilage GPU de la semaine précédente (Nsight Systems) avait établi que `cudaMalloc/cudaFree` représentait 70–80 % du temps API CUDA total, constituant la cause principale de la sous-performance GPU pour les petits problèmes (`s ≤ 90`).

---

## I. Cause racine et analyse

### 1.1 Données de profilage

Résumé Nsight Systems pour `-s 30 -i 10` :

| Appel API | Part du temps total | Nombre d'appels |
|-----------|---------------------|-----------------|
| `cudaMalloc` + `cudaFree` | ~75 % | ~337 |
| Tous les noyaux CUDA | ~0,7 % | ~350 |

**Conclusion** : l'overhead d'allocation mémoire dépasse de loin le calcul effectif. Le GPU passe 90 %+ de son temps à gérer la mémoire plutôt qu'à calculer.

### 1.2 Inventaire complet des allocations par pas de temps

Avant l'optimisation, les `Kokkos::View` suivantes étaient allouées dynamiquement à chaque pas de temps :

| Origine | Nom de la View | Taille | Occurrences/pas |
|---------|----------------|--------|-----------------|
| `EvalEOSForElems` (par région) | `regElemList` | `numElemReg` | 11 (11 régions par défaut) |
| `IntegrateStressForElems` | `fx/fy/fz_elem` | `numElem × 8` | 3 |
| `CalcHourglassControlForElems` | `hg_fx/fy/fz_elem` | `numElem × 8` | 3 |
| `CalcVolumeForceForElems` | `determ` | `numElem` | 1 |
| `LagrangeElements` | `vnew` | `numElem` | 1 |
| `AllocateGradients` (viscosité) | `delx/delv_xi/eta/zeta` | `numElem / allElem` | 6 |
| `AllocateStrains` (cinématique) | `dxx/dyy/dzz` | `numElem` | 3 |
| **Total** | | | **~28/pas** |

---

## II. Implémentation de P1

### 2.1 Principe

Toutes les `View` transitoires ci-dessus sont promues en membres de `Domain`, allouées une seule fois dans le constructeur et réutilisées à chaque pas de temps, supprimant tout `cudaMalloc/cudaFree` à l'exécution.

### 2.2 Modifications de `include/lulesh.h`

**① Ajout des listes d'indices de région côté device dans `ElemConnectivity`**

```cpp
struct ElemConnectivity {
    // ... membres existants ...
    std::vector<std::vector<Index_t>> m_regElemlist;     // côté hôte (conservé)
    std::vector<Kokkos::View<Index_t*>> m_regElemlist_d; // ← nouveau : copies device (P1)
} m_conn;
```

**② Ajout de `ScratchViews` dans `ElemState`**

```cpp
struct ElemState {
    // ... membres existants ...

    struct ScratchViews {
        Kokkos::View<Real_t*> m_vnew;                            // volume relatif (numElem)
        Kokkos::View<Real_t*> m_determ;                          // déterminant Jacobien (numElem)
        Kokkos::View<Real_t*> m_fx_elem, m_fy_elem, m_fz_elem;  // scatter contraintes (numElem×8)
        Kokkos::View<Real_t*> m_hg_fx,   m_hg_fy,   m_hg_fz;   // scatter sablier (numElem×8)
        void reserve(Index_t numElem) { /* allocation unique */ }
    } m_scratch;

    struct EosTemps { /* existant, conservé */ } m_eosTemps;
} m_elems;
```

**③ Gradients et déformations alloués à la construction**

```cpp
// Méthodes publiques converties en no-ops (les sites d'appel restent inchangés)
void AllocateGradients(Int_t, Int_t) {}   // P1 : déjà alloué dans le constructeur
void DeallocateGradients() {}
void AllocateStrains(Int_t) {}
void DeallocateStrains() {}
```

**④ Nouvel accesseur et méthode privée**

```cpp
// Accesseur public
Kokkos::View<Index_t*>& regElemlistDevice(Int_t r) {
    return m_conn.m_regElemlist_d[r];
}

// Privé (appelé uniquement depuis le constructeur)
void AllocateScratch(Int_t numElem, Int_t allElem);
```

### 2.3 Modifications de `src/lulesh-init.cc`

Ajout dans le constructeur après `CreateRegionIndexSets` :

```cpp
// P1-A : transfert unique des 11 listes de région vers le device
m_conn.m_regElemlist_d.resize(numReg());
for (Int_t r = 0; r < numReg(); ++r) {
    Kokkos::View<const Index_t*, Kokkos::HostSpace>
        h(m_conn.m_regElemlist[r].data(), regElemSize(r));
    m_conn.m_regElemlist_d[r] =
        Kokkos::View<Index_t*>("regElemList_r", regElemSize(r));
    Kokkos::deep_copy(m_conn.m_regElemlist_d[r], h);
}

// P1-B : pré-allocation de toutes les Views temporaires par pas de temps
Int_t allElem = numElem()
              + 2*sizeX()*sizeY()
              + 2*sizeX()*sizeZ()
              + 2*sizeY()*sizeZ();
AllocateScratch(numElem(), allElem);
```

### 2.4 Modifications des modules de calcul

| Fichier | Avant | Après |
|---------|-------|-------|
| `lulesh-eos.cc` | `Kokkos::View<Index_t*> regElemList("...", n); deep_copy(...)` | `Kokkos::View<Index_t*> regElemList = domain.regElemlistDevice(r)` |
| `lulesh-integration.cc` | `Kokkos::View<Real_t*> vnew("vnew", numElem)` | `auto& vnew = domain.m_elems.m_scratch.m_vnew` |
| `lulesh-stress.cc` (IntegrateStress) | `Kokkos::View<Real_t*> fx_elem("fx_elem", n8)` ×3 | `auto& fx_elem = domain.m_elems.m_scratch.m_fx_elem` etc. |
| `lulesh-stress.cc` (CalcHourglass) | `Kokkos::View<Real_t*> fx_elem("hg_fx_elem", n8)` ×3 | `auto& fx_elem = domain.m_elems.m_scratch.m_hg_fx` etc. |
| `lulesh-stress.cc` (CalcVolumeForce) | `Kokkos::View<Real_t*> determ("determ", numElem)` | `auto& determ = domain.m_elems.m_scratch.m_determ` |
| `lulesh-viscosity.cc` | `domain.AllocateGradients(...)` / `DeallocateGradients()` | no-ops (supprimés automatiquement) |
| `lulesh-kinematics.cc` | `domain.AllocateStrains(...)` / `DeallocateStrains()` | no-ops (supprimés automatiquement) |

### 3.2 Performance OpenMP (référence, pas le backend cible)

| Taille | Avant P1 (base W13) | Après P1 | Variation |
|--------|---------------------|----------|-----------|
| `-s 45 -i 200` | 3,30 s / 5 518 z/s | 2,12 s / 8 589 z/s | **+56 %** |

> Le backend OpenMP bénéficie également : `AllocateGradients/Strains` générait des `new/delete` répétés même sur CPU.

### 3.3 Gain prévu sur GPU

D'après les données de profilage, P1 devrait éliminer les ~75 % du temps API CUDA imputables à `cudaMalloc/cudaFree`, portant la fraction de calcul effectif de ~0,7 % à ~70 %+ pour les petits problèmes (`s = 30`). Les chiffres précis seront confirmés lors des tests sur Linux + RTX 4070 Laptop.

## IV. Points techniques clés

### 4.1 Sémantique de copie de `Kokkos::View`

`auto& vnew = domain.m_elems.m_scratch.m_vnew` est une référence — aucune allocation supplémentaire. Lors du passage par valeur à une fonction, seules les métadonnées (pointeur + extent) sont copiées ; la mémoire device sous-jacente reste partagée. C'est exactement la sémantique des Views locales précédentes.

### 4.2 Sécurité de la boucle sérielle sur les régions

La boucle EOS sur les 11 régions est sérielle (`for (Int_t r = 0; r < numReg(); r++)`). Les Views de `m_scratch` sont utilisées exclusivement par une région à la fois — aucune course aux données. Ce design reproduit exactement celui d'`EosTemps` (déjà en place depuis W12).

### 4.3 `allElem` inclut les cellules fantômes

Le paramètre `allElem` de `AllocateGradients` = `numElem + 6 × faces fantômes`, nécessaire pour les Views de gradient de vitesse (`delv_xi/eta/zeta`) qui sont indexées par des éléments voisins au-delà des frontières. Dans le cas mono-domaine (sans MPI), les cellules fantômes ne sont pas écrites, mais l'allocation doit couvrir cette plage pour éviter tout accès hors limites.
