## 一、原始 LULESH 2.0 MPI 实现的参考分析

实现前对原始 LULESH 2.0（LLNL/LULESH GitHub 仓库）进行了系统性分析，明确以下设计决策作为本次实现的参照：

### 1.1 通信模式

原始版本采用 **3D 笛卡尔域分解**，进程数须为整数的三次方（1、8、27……）。每个进程最多与 26 个邻居通信（6 面 + 12 边 + 8 角）。本次实现仅保留 **6 面通信**，因为 GPU port 的元素连通性（`lxim/lxip/letam/letap/lzetam/lzetap`）只引用一层深度的 ghost 单元，边和角不涉及。

### 1.2 通信类型

| 消息类型 | 标签常量 | 数据 | 解包方式 |
|---------|---------|------|---------|
| `MSG_COMM_SBN` | 1024 | 节点力（fx/fy/fz） | **scatter-add**（累加到共享边界节点） |
| `MSG_MONOQ` | 3072 | 速度梯度（delv_xi/eta/zeta） | **直接覆写**（写入预分配的 ghost 元素槽） |

### 1.3 非阻塞通信策略

与原始版本一致，使用 `MPI_Irecv` + `MPI_Isend` + `MPI_Wait/Waitall`，避免串行化；先发布所有接收请求（`CommRecv`），再发送（`CommSend`），最后等待并解包（`CommSBN` / `CommMonoQ`）。

### 1.4 时间步全局归约

每个时间步结束时，各进程的局部 courant 约束和 hydro 约束需要通过 `MPI_Allreduce(MPI_MIN)` 合并为全局最小值，确保所有进程使用一致的 `deltatime`。

## 三、lulesh-comm.cc 核心实现

### 3.1 DomainComm 全局结构体

为避免将 MPI 类型（`MPI_Request` 等）污染 `Domain` 类定义，将通信状态提取为独立结构体，定义在 `lulesh.h` 末尾并以 `extern` 声明：

```cpp
struct DomainComm {
    Real_t      *sendBuf ;
    Real_t      *recvBuf ;
    MPI_Request  recvRequest[6] ;
    MPI_Request  sendRequest[6] ;
} ;
extern DomainComm g_comm ;
```

缓冲区大小按节点面积（`(nx+1)²`）分配，确保节点力交换（面积最大）不会越界。

### 3.2 面编号与邻居映射

6 个面按固定顺序编号，对应 3D 笛卡尔网格中的 `(dc, dr, dp)` 偏移：

| 编号 | 面方向 | 偏移 `(dc,dr,dp)` | 大小 |
|------|-------|-----------------|------|
| 0 | planeMin (zeta-) | (0, 0, -1) | dx×dy |
| 1 | planeMax (zeta+) | (0, 0, +1) | dx×dy |
| 2 | rowMin (eta-)   | (0, -1, 0) | dx×dz |
| 3 | rowMax (eta+)   | (0, +1, 0) | dx×dz |
| 4 | colMin (xi-)    | (-1, 0, 0) | dy×dz |
| 5 | colMax (xi+)    | (+1, 0, 0) | dy×dz |

邻居 rank 计算：`plane×tp² + row×tp + col`，其中 `tp = ∛numRanks`。

### 3.3 CommSend 打包逻辑

打包时以传入的 `dx/dy/dz` 作为循环边界和数组步长（同时适用于元素空间 `nx` 和节点空间 `nx+1`），避免两套索引代码：

```cpp
// face=0: planeMin，发送 k=0 平面
for (fld in fields)
    for j in [0, dy): for i in [0, dx):
        buf[idx++] = fieldData[fld][j*dx + i];

// face=1: planeMax，发送 k=dz-1 平面
for (fld in fields)
    for j in [0, dy): for i in [0, dx):
        buf[idx++] = fieldData[fld][(dz-1)*dy*dx + j*dx + i];
```

### 3.4 CommSBN 解包（scatter-add）

节点力在进程边界上被多个进程重复计算，接收到邻居的贡献后需要累加而非覆写：

```cpp
// face=0: 接收来自 zeta- 邻居的 k=0 平面节点力
for (fld in fields)
    for j in [0, EN): for i in [0, EN):
        fieldData[fld][j*EN + i] += recvBuf[idx++];  // 累加
```

### 3.5 CommMonoQ 解包（直接覆写 ghost）

速度梯度的 ghost 元素槽已由 `SetupBoundaryConditions` 预分配在 `numElem` 之后，接收数据直接写入：

```cpp
// ghostBase[face] = numElem + 前面所有 ghost 面的累计大小
for (e in [0, faceSize)):
    dxi_h(ghostBase[face] + e)   = buf[3*e    ];
    deta_h(ghostBase[face] + e)  = buf[3*e + 1];
    dzeta_h(ghostBase[face] + e) = buf[3*e + 2];
// 写回 device
Kokkos::deep_copy(domain.m_elems.m_delv_xi, dxi_h);
```

## 四、GPU-MPI 协同的数据流

每个时间步的通信点均遵循相同的三段式模式：

```
GPU 计算 → Kokkos::deep_copy(GPU→host) → MPI 通信 → Kokkos::deep_copy(host→GPU) → 下一步 GPU 计算
```

**通信点 1**（`LagrangeNodal` 中）：

```
CalcForceForNodes()         ← GPU 计算节点力
  deep_copy fx/fy/fz → host mirror
  CommRecv(MSG_COMM_SBN, dx=EN, dy=EN, dz=EN)
  CommSend(MSG_COMM_SBN, fields=[fx,fy,fz])
  CommSBN()                 ← Wait + scatter-add
  deep_copy fx/fy/fz → device
CalcAccelerationForNodes()  ← GPU 使用更新后的节点力
```

**通信点 2**（`CalcQForElems` 中）：

```
CalcMonotonicQGradientsForElems()   ← GPU 计算速度梯度
  deep_copy delv_xi/eta/zeta → host
  CommRecv(MSG_MONOQ, dx=nx, dy=ny, dz=nz)
  CommSend(MSG_MONOQ, fields=[dxi,deta,dzeta])
  CommMonoQ()              ← Wait + 写入 ghost 槽 + deep_copy → device
CalcMonotonicQForElems()   ← GPU 读取包含 ghost 的完整梯度数组
```

**通信点 3**（`TimeIncrement` 中）：

```
MPI_Allreduce(&gnewdt, &newdt, MPI_MIN)  ← 全局最小时间步
```

## 五、调试过程与 Bug 修复

### 5.1 MPI 成员访问权限错误

**现象**：首次编译报 `'m_colLoc' is a private member of 'Domain'`，共 20 个访问错误。

**原因**：最初将 `commDataSend/Recv` 和 `MPI_Request[6]` 放入 `Domain` 的 `private` 区，`lulesh-comm.cc` 作为外部翻译单元无法访问；同时 `m_rowMin/Max` 等也缺少公开访问器。

**修复**：将 MPI 状态提取为 `DomainComm g_comm` 全局结构体（完全绕过访问控制问题）；在 `lulesh.h` 中为 6 个边界标志新增 `rowMin()/rowMax()/colMin()/colMax()/planeMin()/planeMax()` 访问器。

### 5.2 sendRequest 未初始化导致 Segfault

**现象**：单进程运行（无实际邻居）时在 `MPI_Waitall` 处 Segfault，地址 `0x38`。

**原因**：`CommSend` 对无邻居的面跳过了 `MPI_Isend`，对应的 `sendRequest[face]` 保持未初始化状态，`MPI_Waitall` 读取垃圾值。

**修复**：在 `CommSend` 循环前预置所有请求为 `MPI_REQUEST_NULL`：

```cpp
for (int face = 0; face < 6; ++face)
    g_comm.sendRequest[face] = MPI_REQUEST_NULL;
```

### 5.3 通信缓冲区大小不足导致内存越界

**现象**：`CommSetup` 以元素面积（`nx×ny`）分配缓冲区，但节点力交换使用节点面积（`(nx+1)²`），缓冲区溢出，破坏相邻内存，导致多进程下 Kokkos OpenMP 核函数在 `IntegrateStressForElems` 中崩溃（Segfault，地址 `0x0`）。

**修复**：缓冲区大小改按节点面积计算（节点面始终大于元素面）：

```cpp
Index_t EN = domain.sizeX() + 1;
Index_t bufSize = 3 * 6 * EN * EN;  // 节点面积 > 元素面积
```

## 七、技术决策

### 1. DomainComm 全局结构体而非 Domain 成员

将 MPI 状态放入全局结构体而不是 `Domain` 类，原因：（a）避免 `lulesh.h` 在 `USE_MPI=0` 时引入 MPI 头文件；（b）`Domain` 类已有大量 `public` GPU 数据成员，MPI 状态语义上属于运行时通信层，分离符合职责单一原则。

### 2. 仅实现 6 面通信

原始 LULESH 2.0 实现了完整的 26 邻居（面+边+角）通信。GPU port 中元素连通性 `lxim/lxip` 等仅指向面邻居 ghost 元素，边和角 ghost 不被访问。因此 6 面通信在数值上是完备的，同时大幅降低实现复杂度。

### 3. dx/dy/dz 参数统一元素和节点索引

`CommSend` 以 `dx/dy/dz` 作为循环边界和数组步长。节点力交换时 `dx=ny=nz=nx+1`，元素梯度交换时 `dx=dy=dz=nx`。两种情况共用同一套打包代码，消除代码重复。

### 4. GPU-MPI 边界处理策略

当前选择最保守的策略：在通信点做显式 `deep_copy`（GPU→host，host→GPU）。此策略在 CUDA-aware MPI 不可用时完全正确，并为后续优化（使用 CUDA-aware MPI 直接传输 device 指针，或与 GPU 计算重叠通信）预留了接口。
