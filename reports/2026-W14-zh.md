# 周报 2026-W14~W15 | LULESH 2.0 GPU 优化 P1 + P2

**周期**：2026-03-30 ~ 2026-04-12
**项目**：LULESH 2.0 高性能计算代理应用（Kokkos 5 / GPU 迁移，`gpu-port` 分支）
**平台**：macOS Apple Silicon（OpenMP 后端本地验证）；目标平台：Linux + RTX 4070 Laptop GPU（CUDA 后端）
**正确性基准**：`OMP_PROC_BIND=close ./build/lulesh2.0 -s 10 -i 50` → `Final Origin Energy = 8.104796e+04`

---

## 本周工作概览

两周合并报告，覆盖两项 GPU 性能优化：

- **P1**（W14）：通过在 `Domain` 构造函数中一次性预分配全部瞬态 `Kokkos::View`，将原先每个时间步约 28 次 `cudaMalloc + cudaFree` 调用归零。
- **P2**（W15）：针对 P1 测试后 Nsight Compute 剖析揭示的两个剩余瓶颈——SM 寄存器压力（占用率 25%）和 scatter-gather 模式带宽开销——进行修正。P2 包含一轮初版实现、GPU 测试、失效分析和修正三个子阶段。

---

## 一、P1：问题根因与分析

### 1.1 剖析数据

Nsight Systems 对 `-s 30 -i 10` 的统计：

| API 调用 | 总耗时占比 | 调用次数 |
|----------|-----------|---------|
| `cudaMalloc` + `cudaFree` | ~75% | ~337 次 |
| 所有 CUDA 内核执行 | ~0.7% | ~350 次 |

结论：内存分配开销远超实际计算，GPU 的 90%+ 时间花费在内存管理而非数值计算上。

### 1.2 每步分配源头（完整清单）

| 来源 | View 名称 | 大小 | 次数/步 |
|------|-----------|------|--------|
| `EvalEOSForElems`（每区域） | `regElemList` | `numElemReg` | 11（默认 11 区域）|
| `IntegrateStressForElems` | `fx/fy/fz_elem` | `numElem × 8` | 3 |
| `CalcHourglassControlForElems` | `hg_fx/fy/fz_elem` | `numElem × 8` | 3 |
| `CalcVolumeForceForElems` | `determ` | `numElem` | 1 |
| `LagrangeElements` | `vnew` | `numElem` | 1 |
| `AllocateGradients`（viscosity） | `delx/delv_xi/eta/zeta` | `numElem / allElem` | 6 |
| `AllocateStrains`（kinematics） | `dxx/dyy/dzz` | `numElem` | 3 |
| **合计** | | | **~28/步** |

## 二、P1：优化实现

### 2.1 设计思路

将上述全部瞬态 `View` 提升为 `Domain` 的成员变量，在构造函数中一次分配，后续每步复用，彻底消除运行期 `cudaMalloc/cudaFree`。

### 2.2 `include/lulesh.h` 修改

**① `ElemConnectivity` 新增设备端区域索引列表**

```cpp
struct ElemConnectivity {
    std::vector<std::vector<Index_t>> m_regElemlist;    // 宿主端（保留）
    std::vector<Kokkos::View<Index_t*>> m_regElemlist_d; // ← 新增：设备端副本（P1）
} m_conn;
```

**② `ElemState` 新增 `ScratchViews` 结构体**

```cpp
struct ScratchViews {
    Kokkos::View<Real_t*> m_vnew;    // 相对体积（numElem）
    Kokkos::View<Real_t*> m_determ;  // Jacobi 行列式（numElem）
    void reserve(Index_t numElem) { /* 一次性分配 */ }
} m_scratch;
```

**③ 4 个 Allocate/Deallocate 方法改为无操作**

```cpp
void AllocateGradients(Int_t, Int_t) {}
void DeallocateGradients() {}
void AllocateStrains(Int_t) {}
void DeallocateStrains() {}
```

### 2.3 各计算模块修改

| 文件 | 原代码 | 修改后 |
|------|--------|--------|
| `lulesh-eos.cc` | 每步 `deep_copy` 区域索引 | `domain.regElemlistDevice(r)`（构造时上传） |
| `lulesh-integration.cc` | `Kokkos::View<Real_t*> vnew("vnew", numElem)` | `auto& vnew = domain.m_elems.m_scratch.m_vnew` |
| `lulesh-stress.cc`（IntegrateStress） | `fx/fy/fz_elem` 局部 View ×3 | scratch View |
| `lulesh-stress.cc`（CalcHourglass） | `hg_fx/fy/fz` 局部 View ×3 | scratch View |
| `lulesh-stress.cc`（CalcVolumeForce） | `determ` 局部 View | `domain.m_elems.m_scratch.m_determ` |

## 四、P2：GPU 测试结果与失效分析

P1 在 RTX 4070 Laptop 上测试通过后，进行 Nsight Compute 深度剖析，识别出新瓶颈，并制定 P2 优化方案。

### 4.1 P2 初版 FOM 数据（GPU）

| 规模 | P1（基准） | P2 初版 | 变化 |
|------|-----------|---------|------|
| `-s 30` | 12,687 z/s | 10,561 z/s | **−17%** |
| `-s 45` | 21,341 z/s | 22,848 z/s | **+7%** |

结果矛盾，说明初版方案存在缺陷。

### 4.2 ncu 主要内核指标

| 内核 | 寄存器/线程 | SM 占用率 | 计算吞吐量 |
|------|------------|----------|----------|
| `CalcHourglassControlForElems` | 168 | **25%** | 88% |
| `CalcKinematicsAndLagrange` | 144 | **25%** | 85% |
| `CalcMonotonicQGradientsForElems` | 118 | **33%** | — |
| `IntegrateStressForElems` | — | — | 81% |

初版 `LaunchBounds<256,2>` 对寄存器数量**没有任何效果**，contribute 步骤 DRAM 带宽占用 **93%**。

### 4.3 P2-A 失效原因：LaunchBounds 约束过松

`LaunchBounds<maxT, minB>` 约束：`minB × threadsPerBlock × R ≤ 65536`

```
LaunchBounds<256,2>：2 × 128 × R ≤ 65536  →  R ≤ 256  （168 < 256，无约束效果）
LaunchBounds<128,4>：4 × 128 × R ≤ 65536  →  R ≤ 128  （168 > 128，触发溢出）
```

### 4.4 P2-B 问题：ScatterView 默认模式的歧义

ncu 显示 `l1tex__t_bytes_pipe_lsu_mem_global_op_atom.sum = 0`，contribute 步骤 93% DRAM 带宽。

初步判断：`create_scatter_view()` 在 CUDA 上默认 `ScatterDuplicated + ScatterNonAtomic`（线程私有副本 + 归约），contribute 归约步骤成为新带宽瓶颈，并造成 `s=30` 退化。

> **不确定性**：sm_89 上全局内存原子操作绕过 L1 走 L2，`l1tex__...atom = 0` 是正常现象，不能直接证明未用原子操作。正确验证指标为 `l2__global_atomic_requests.sum`（本次未测量）。

### 4.5 新发现目标：`CalcMonotonicQGradientsForElems`

118 寄存器/线程，33% SM 占用率，此前未列为优化对象，本次纳入 P2-D。

## 五、P2：修正实现

### 5.1 P2-A 修正：`LaunchBounds<128,4>`（三处）

```cpp
// src/lulesh-stress.cc — CalcHourglassControlForElems
using hg_policy_t  = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;

// src/lulesh-kinematics.cc — CalcKinematicsAndLagrange
using kin_policy_t = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;

// src/lulesh-viscosity.cc — CalcMonotonicQGradientsForElems（P2-D）
using mono_policy_t = Kokkos::RangePolicy<Kokkos::LaunchBounds<128, 4>>;
```

### 5.2 P2-B 修正：显式 `ScatterNonDuplicated + ScatterAtomic`

```cpp
using node_sv_t = Kokkos::Experimental::ScatterView<Real_t*,
    typename decltype(fx_v)::array_layout,
    typename decltype(fx_v)::execution_space,
    Kokkos::Experimental::ScatterSum,
    Kokkos::Experimental::ScatterNonDuplicated,
    Kokkos::Experimental::ScatterAtomic>;
node_sv_t fx_scatter(fx_v);
```

`ScatterNonDuplicated` 下写入直接通过原子操作更新底层 View，`contribute()` 退化为无操作，消除 93% DRAM 的 contribute 步骤。

## 六、技术要点

### 6.1 `Kokkos::View` 复制语义（P1）

`auto& vnew = domain.m_elems.m_scratch.m_vnew` 中 `auto&` 是引用，不额外分配内存。传入函数时按值传递 `Kokkos::View`，复制的是元数据（指针 + extent），底层设备内存仍共享。

### 6.2 `allElem` 包含幽灵单元（P1）

`AllocateGradients` 的 `allElem` = `numElem + 6×面幽灵`，用于速度梯度 View 的跨面查询，防止越界。

### 6.3 LaunchBounds 是提示而非强制（P2）

编译器可通过寄存器溢出满足约束，溢出带来的 L1 缓存流量可能部分抵消占用率提升的收益，需实测验证。

### 6.4 多处修改同步上线（P2）

三处 LaunchBounds + 两处 ScatterView 同步修改，若 GPU 结果不符预期，无法直接定位原因，建议后续逐项对比。
