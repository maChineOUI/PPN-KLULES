## 一、迁移的核心模式

所有核函数的改造遵循统一模式：

**改前（CPU-only）**
```cpp
void SomeKernel(Domain& domain, ...) {
    Kokkos::parallel_for("label", N, [&](Index_t i) {
        // 直接通过 domain.m_xxx.m_yyy(i) 访问
        // 调用 domain.someMethod() 等宿主函数
    });
}
```

**改后（GPU 兼容）**
```cpp
void SomeKernel(Domain& domain, ...) {
    // 1. 在 lambda 外提取所需 View 为局部变量
    auto x_v = domain.m_nodes.m_x;
    auto y_v = domain.m_nodes.m_y;
    // ...
    // 2. KOKKOS_LAMBDA = [=]，值捕获 View 句柄（元数据可拷贝）
    Kokkos::parallel_for("label", N, KOKKOS_LAMBDA(Index_t i) {
        Real_t xi = x_v(i);
    });
}
```

`[=]` 捕获 `Kokkos::View` 时仅拷贝其元数据（指针 + extent），不拷贝底层数据。GPU 上通过该元数据直接访问设备内存，OpenMP 上则直接访问宿主内存，两者行为一致。

### 2.1 `lulesh-timestep.cc`

**函数**：`CalcCourantConstraintForElems`、`CalcHydroConstraintForElems`

提取 3 个 View（`vdov_v`、`ss_v`、`arealg_v`），将 `[&]` 改为 `KOKKOS_LAMBDA`，替换 `std::sqrt` → `Kokkos::sqrt`，`std::fabs` → `Kokkos::fabs`。归约操作保持 `Kokkos::Min<Real_t>` 双 reducer（W11 已优化），本次仅更新捕获方式。

### 2.2 `lulesh-viscosity.cc`

**函数**：`CalcMonotonicQGradientsForElems`、`CalcMonotonicQForElems`

`CalcMonotonicQGradientsForElems`：提取 14 个 View，`KOKKOS_LAMBDA`，通过 View 的 `.data()` 指针偏移访问节点连通性（`nodelist_v.data() + 8*i`），`vnew[i]` → `vnew(i)`。

`CalcMonotonicQForElems`：`KOKKOS_LAMBDA`。原代码在 `switch-default` 分支中使用 `fprintf(stderr, ...)`，在设备端非法，替换为 `Kokkos::abort`：

```cpp
// 改前
default:
    fprintf(stderr, "ERROR: Unknown region type %d\n", domain.regCSR(r));
    exit(-1);
// 改后
default:
    Kokkos::abort("CalcMonotonicQForElems: unknown region type");
```

### 2.3 `lulesh-kinematics.cc`

**函数**：`CalcElemVelocityGradient`、`CalcLagrangeElements`

`CalcElemVelocityGradient`：`static inline` → `KOKKOS_INLINE_FUNCTION static`，使其可在设备端核函数中调用。

`CalcLagrangeElements`：提取 15 个 View，`KOKKOS_LAMBDA`。原代码在 lambda 内调用 `CollectDomainNodesToElemNodes(domain, ...)`，该函数接受 `Domain&`（宿主对象），不可在设备端调用。改为内联 8 节点收集循环：

```cpp
// 改前（调用宿主函数）
CollectDomainNodesToElemNodes(domain, elemToNode, x_local, y_local, z_local);
// 改后（内联，GPU 可用）
const Index_t* elemToNode = nodelist_v.data() + 8*k;
for (Index_t n = 0; n < 8; ++n) {
    Index_t gn = elemToNode[n];
    x_local[n] = x_v(gn);
    y_local[n] = y_v(gn);
    z_local[n] = z_v(gn);
}
```

`exit(VolumeError)` → `Kokkos::abort("VolumeError: ...")`。

### 2.4 `lulesh-nodal.cc`

共 4 个 `Kokkos::parallel_for`，均提取所需 View，改为 `KOKKOS_LAMBDA`，`std::fabs` → `Kokkos::fabs`。

### 2.5 `lulesh-eos.cc`

`CalcEnergyForElems`：签名从 14 个裸指针改为 14 个 `Kokkos::View<Real_t*>`，内部改为 `KOKKOS_LAMBDA`，`std::fabs/sqrt` → `Kokkos::fabs/sqrt`。

`EvalEOSForElems`：`regElemList`（宿主原始指针）用无管理 View 包装，OpenMP 下零拷贝；CUDA 后端需 `deep_copy`（注释已标注）：

```cpp
Kokkos::View<Index_t*> regElemList(regElemRaw, numElemReg);
```

`ApplyMaterialPropertiesForElems`：`exit(VolumeError)` → `Kokkos::abort`，`vnew[i]` → `vnew(i)`。

### 2.6 `lulesh-stress.cc`

`SumElemStressesToNodeForces` 和 `CalcElemFBHourglassForce`：`static inline` → `KOKKOS_INLINE_FUNCTION static`。

`IntegrateStressForElems`：scatter buffer 改为 `Kokkos::View<Real_t*>`；移除原有的 `numthreads > 1` 条件分支（单线程优化路径，在 GPU 上会导致竞争条件），统一使用 scatter/gather：

```cpp
// 改前：CPU 条件分支
if (numthreads > 1) { /* scatter → gather */ }
else               { /* 直接写 fx/fy/fz（GPU 上 race condition）*/ }
// 改后：统一 scatter/gather
Kokkos::View<Real_t*> fx_elem("fx_elem", numElem8);
// scatter kernel ... gather kernel ...
```

## 三、构建与链接错误修复

完成全部 6 个文件改造后首次构建，出现链接错误：

```
Undefined symbols for architecture arm64:
  "CalcElemVolume(double const*, ...)", referenced from:
      CalcLagrangeElements(...) in lulesh-kinematics.cc.o
  "CalcElemNodeNormals(...)", referenced from:
      IntegrateStressForElems(...) in lulesh-stress.cc.o
ld: symbol(s) not found for architecture arm64
```

**根本原因**：`KOKKOS_INLINE_FUNCTION` 展开后含 `inline`，C++ ODR 规则要求 `inline` 函数的定义在每个调用它的翻译单元中可见。几何函数定义在 `src/lulesh-geometry.cc`，但调用方只有头文件中的声明，链接器找不到实体。

**修复**：将所有 `KOKKOS_INLINE_FUNCTION` 几何函数的定义从 `.cc` 移入 `include/lulesh-geometry.h`，`CollectDomainNodesToElemNodes`（宿主函数，无 `KOKKOS_INLINE_FUNCTION`）保留在 `.cc`。修复后链接成功。

## 五、技术决策

### 1. `KOKKOS_INLINE_FUNCTION` 函数定义必须在头文件中

C++ `inline` 规则与 Kokkos 设备函数要求共同决定：设备端函数必须在编译期对调用方可见，必须定义在头文件中，不能定义在 `.cc` 文件中。

### 2. `CollectDomainNodesToElemNodes` 的内联替代

该函数接受 `Domain&`（宿主引用），在所有调用点替换为内联 8 节点循环，是最小修改代价的方案，完全保留语义。

### 3. scatter buffer `numthreads > 1` 分支移除

原分支是 CPU-only 优化（单线程下省略 scatter）。GPU 上所有线程并行，直接写模式会导致竞争条件，scatter/gather 是唯一正确路径。

### 4. `regElemList` 的 `deep_copy` 修复

初版使用无管理 View 包装宿主原始指针（OpenMP 下零拷贝），CUDA 后端会将该宿主指针注册为 CudaSpace View，GPU 内核读取时崩溃。修复为显式 `deep_copy`：

```cpp
Kokkos::View<const Index_t*, Kokkos::HostSpace> regElemList_h(regElemRaw, numElemReg);
Kokkos::View<Index_t*> regElemList("regElemList", numElemReg);
Kokkos::deep_copy(regElemList, regElemList_h);
```

## 六、CUDA 构建完整调试记录

### 6.1 第一轮错误：`--expt-extended-lambda` 缺失

**现象**：

```
FunctorType = lambda [](Index_t)->void
calling a constexpr __host__ function from a __device__ function is not allowed.
```

`KOKKOS_LAMBDA` 展开为 `[=] __host__ __device__` 依赖 nvcc 的 `--expt-extended-lambda` 标志，该标志由 Kokkos 在 `Kokkos_ENABLE_CUDA_LAMBDA=ON` 时自动传入。Linux 安装未开启此选项，lambda 仅含 `__host__`。

**初步修复**：在 `CMakeLists.txt` CUDA 分支中显式添加该标志：

```cmake
target_compile_options(lulesh PRIVATE
    $<$<COMPILE_LANGUAGE:CUDA>:--expt-extended-lambda>
)
```

### 6.2 第二轮错误：`_OPENMP` 宏未定义

**现象**：`#error "You enabled Kokkos OpenMP support without enabling OpenMP in the compiler!"`

**原因**：Kokkos 以 OPENMP+CUDA 双后端安装。nvcc 编译 CUDA 语言文件时不自动传 `-fopenmp` 给宿主编译器，`_OPENMP` 宏未定义。

**修复**：在 CUDA 编译选项中添加：

```cmake
$<$<COMPILE_LANGUAGE:CUDA>:-Xcompiler=-fopenmp>
```

### 6.3 第三轮错误：lambda 名称 `_INTERNAL_` 前缀

**现象**：

```
template argument 1 is invalid
FunctorType = lambda []( ::, ...)->void
```

**根本原因**：对 `.cc` 源文件设置 `LANGUAGE CUDA` 属性后，CMake 将其路由给 `CMAKE_CUDA_COMPILER`（nvcc 直接调用），而非 `CMAKE_CXX_COMPILER`（nvcc_wrapper）。nvcc 直接处理 `.cc` 文件时，给 lambda 添加 `_INTERNAL_` 前缀，cudafe1 无法解析该名称，导致模板参数失效。

**核心区别**：

| 编译路径 | lambda 名称 | 原因 |
|----------|-------------|------|
| nvcc_wrapper（CXX 路径） | 正常外部链接名 | nvcc_wrapper 内部将 `.cc` 重命名为 `.cu` |
| nvcc 直接（CUDA 路径） | `_INTERNAL_` 前缀 | nvcc 对非 `.cu` 扩展名的文件使用受限名称 |

**修复**：移除所有 `set_source_files_properties(... LANGUAGE CUDA)`，所有源文件保持 CXX 语言，由 nvcc_wrapper 统一处理。`--expt-extended-lambda` 从 `COMPILE_LANGUAGE:CUDA` 移至 `COMPILE_LANGUAGE:CXX`，`-Xcompiler=-fopenmp` 由 `OpenMP::OpenMP_CXX` 经 CXX 路径自动传入，无需显式添加。

`CMakeLists.txt` 最终采用双路径检测：

```cmake
if(CMAKE_CXX_COMPILER MATCHES "nvcc_wrapper")
    # Path A：nvcc_wrapper 为 CXX 编译器（推荐）
    # 所有源文件保持 CXX 语言，nvcc_wrapper 内部处理 CUDA
    target_compile_options(lulesh PRIVATE
        $<$<COMPILE_LANGUAGE:CXX>:--expt-extended-lambda>
    )
else()
    # Path B：g++ + kokkos_launch_compiler（警告：LANGUAGE CUDA 不可设置）
    message(WARNING "使用 nvcc_wrapper 可获得完整支持")
endif()
```

### 6.4 持久错误的根本原因：`KOKKOS_ENABLE_CUDA_LAMBDA=ON` 缺失

上述 CMakeLists.txt 修复后重新构建，仍出现 `FunctorType = lambda [](Index_t)->void`（无 `__device__`）。

**根本原因**：`KOKKOS_LAMBDA` 宏的展开内容在 Kokkos **安装时**确定：

- Kokkos 以 `Kokkos_ENABLE_CUDA_LAMBDA=ON` 构建 → `KOKKOS_LAMBDA` = `[=] __host__ __device__` ✓
- Kokkos 以默认配置构建 → `KOKKOS_LAMBDA` = `[=]`（无 `__device__`）✗

`--expt-extended-lambda` 是 nvcc 接受 `__device__` lambda 的前置条件，但不能为已展开的纯 `[=]` lambda 补充 `__device__` 属性。两者缺一不可。

Linux 机器上的 Kokkos 安装未开启此选项，这是所有 CUDA 构建错误的最终根源。

**解决方案**：在 Linux 机器重建 Kokkos，加入 `Kokkos_ENABLE_CUDA_LAMBDA=ON`：

```bash
cmake -S /path/to/kokkos -B /tmp/kokkos-build \
    -DCMAKE_INSTALL_PREFIX=/path/to/kokkos/install \
    -DKokkos_ENABLE_CUDA=ON \
    -DKokkos_ENABLE_CUDA_LAMBDA=ON \    # ← 关键
    -DKokkos_ENABLE_OPENMP=ON \
    -DKokkos_ARCH_AMPERE80=ON \
    -DCMAKE_CXX_COMPILER=/path/to/kokkos/bin/nvcc_wrapper \
    -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/kokkos-build -j$(nproc) && cmake --install /tmp/kokkos-build
```

LULESH 源码和 `CMakeLists.txt` 无需任何修改，重新指向新 Kokkos 安装路径即可。

## 九、CUDA 运行时调试（三轮）

构建成功后在 Linux + RTX 4070 Super（CUDA arch 89）上首次运行，连续出现三类运行时崩溃，均为宿主端非法访问 CudaSpace `Kokkos::View`。

### 9.1 第一轮：`label="regElemList"` / `label="e"`（EOS 模块）

**现象**：`Kokkos::View ERROR: attempt to access inaccessible memory space (label="e")`

**根因**：`EvalEOSForElems` 中将宿主原始指针直接包装为默认空间 View：

```cpp
// 错误：CudaSpace 下此 View 的数据指针指向宿主内存
Kokkos::View<Index_t*> regElemList(regElemRaw, numElemReg);
```

GPU 内核通过该 View 访问宿主内存 → 非法。

**修复**：`deep_copy` 模式（见 §五.4）。

---

### 9.2 第二轮：`label="e"`（初始化模块，真正根因）

**现象**：相同错误，相同 backtrace 地址，排除第一轮修复未生效的可能后定位至更早的崩溃点。

**根因**：`Domain` 构造函数在分配 View 后立即对其进行标量赋值：

```cpp
// lulesh-init.cc — 在 CUDA 后端直接写 CudaSpace View → 崩溃
for (Index_t i=0; i<numElem(); ++i) {
    e(i) = Real_t(0.0) ;   // label="e" 在此触发
    p(i) = Real_t(0.0) ;
    // ...
}
```

构造函数是程序启动时第一个接触这些 View 的地方，崩溃早于任何 EOS 代码执行。

**受影响范围**：构造函数的零初始化循环、`BuildMesh`（坐标/nodelist）、`SetupThreadSupportStructures`（nodeElemStart/CornerList）、`SetupSymmetryPlanes`（symmX/Y/Z）、`SetupElementConnectivities`（6 个连接关系 View）、`SetupBoundaryConditions`（elemBC + 连接关系修补）、`lulesh-util.cc` 验证输出循环。

**修复模式（三种，按场景选用）**：

| 场景 | 方法 |
|------|------|
| 纯零/常量初始化 | `Kokkos::deep_copy(view, scalar)` |
| 宿主端计算后上传 | `create_mirror_view` → 填充 host mirror → `deep_copy` 回设备 |
| 设备端数据需宿主读取 | `create_mirror_view` + `deep_copy` 拉取 → 读取 host mirror |

同时将 `m_regNumList`、`m_regElemSize` 的类型改为 `Kokkos::View<Index_t*, Kokkos::HostSpace>`，因为这两个数组仅在宿主端区域初始化逻辑中使用，从不进入任何 GPU 内核。

**涉及文件**：`include/lulesh.h`，`src/lulesh-init.cc`（6 个函数），`src/lulesh-util.cc`。

---

### 9.3 第三轮：`label="q"`（黏性模块）

**现象**：`Kokkos::View ERROR: attempt to access inaccessible memory space (label="q")`

**根因**：`CalcQForElems` 在 GPU 内核完成后，从宿主端逐元素读取结果：

```cpp
// 错误：宿主直接读取 CudaSpace View
for (Index_t i=0; i<numElem; ++i) {
    if ( domain.q(i) > domain.qstop() ) { ...
```

**修复**：改为设备端 `parallel_reduce`，不再将数据下载到宿主：

```cpp
auto q_v = domain.m_elems.m_q ;
const Real_t qstop = domain.qstop() ;
Index_t exceeded = 0 ;
Kokkos::parallel_reduce("QStopCheck", numElem,
    KOKKOS_LAMBDA(Index_t i, Index_t& flag) {
        if (q_v(i) > qstop) flag = 1 ;
    },
    Kokkos::Max<Index_t>(exceeded)) ;
if (exceeded > 0) exit(QStopError) ;
```

逻辑等价：检查仅需"是否有元素超限"，无需具体索引。
