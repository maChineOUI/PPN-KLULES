## 一、代码级优化（P1–P6）

### 1.1 优化项清单

本轮在 Kokkos-Comm 基础版本上实施六项代码级改进，每项均保证数学等价性，正确性经 B1–B5 矩阵全部通过验证。

| 编号 | 名称 | 核心改动 | 主要收益 |
|------|------|---------|---------|
| P1 | 删除冗余体积检查内核 | 删除 `CalcVolumeForceForElems_check` 内核（在 `CalcLagrangeElements` 已对 `vnew ≤ 0` 做过检查，determ 检查不可能再触发） | 减少 1 次 kernel launch/步 |
| P2 | 非 MPI 路径恢复 RangePolicy | `USE_MPI=0` 路径中移除每步临时 `allElemsIdx` 索引重建内核，恢复直接 `RangePolicy` | 减少 1 次 kernel launch + 临时 alloc/步 |
| P3 | 预分配 SBN mirror views | `DomainComm` 新增 `sbn_fx_h/fy_h/fz_h`，`CommSetup` 一次性分配，消除每步 `create_mirror_view(fx/fy/fz)` | 消除 ~715 KB malloc/步 |
| P4 | 预分配 vnew + determ | `Domain` 新增持久化 `m_vnew`/`m_determ` View，初始化时分配 | 消除 ~432 KB malloc/步 |
| P5 | 预分配 scatter 缓冲区 | `Domain` 新增 `ScatterBuffers` 结构体，持久化 `fx/fy/fz/hg_fx/hg_fy/hg_fz`（各 `numElem×8`）；`IntegrateStressForElems` 和 `CalcHourglassControlForElems` 改用预分配缓冲 | 消除 ~10.4 MB malloc/步（最大单项） |
| P6 | 融合 ApplyBC 三内核 | 将 `ApplyBC` 的 X/Y/Z 三个独立 `parallel_for` 合并为一个 | 减少 2 次 kernel launch/步 |

### 1.2 ScatterBuffers 结构体（P5 核心实现）

```cpp
struct ScatterBuffers {
    Kokkos::View<Real_t*> fx,    fy,    fz;
    Kokkos::View<Real_t*> hg_fx, hg_fy, hg_fz;
    void reserve(Index_t numElem8) {
        fx    = Kokkos::View<Real_t*>("fx_elem",    numElem8);
        fy    = Kokkos::View<Real_t*>("fy_elem",    numElem8);
        fz    = Kokkos::View<Real_t*>("fz_elem",    numElem8);
        hg_fx = Kokkos::View<Real_t*>("hg_fx_elem", numElem8);
        hg_fy = Kokkos::View<Real_t*>("hg_fy_elem", numElem8);
        hg_fz = Kokkos::View<Real_t*>("hg_fz_elem", numElem8);
    }
} m_scatter;
```

### 1.3 DomainComm 最终结构（本周末状态）

O1/O2/O3 实施后又经单变量测试证伪并回退，最终结构如下：`dt_send_pair`/`dt_recv_pair` 保留（KokkosComm allreduce 所需），O3 的 `interiorNodes`/`boundaryNodes` 已移除。

```cpp
struct DomainComm {
    using execution_space   = Kokkos::DefaultExecutionSpace;
    using communicator_type = KokkosComm::Communicator<KokkosComm::MpiSpace, execution_space>;
    using request_type      = KokkosComm::Request<KokkosComm::MpiSpace>;
#ifdef KOKKOS_ENABLE_CUDA
    using buffer_type = Kokkos::View<Real_t*, Kokkos::CudaHostPinnedSpace>;
#else
    using buffer_type = Kokkos::View<Real_t*, Kokkos::HostSpace>;
#endif
    std::optional<communicator_type>  sbnComm, monoqComm;
    buffer_type  sendBuf, recvBuf;
    std::array<request_type, 6> recvRequest, sendRequest;
    // KokkosComm allreduce 的 staging 缓冲区（dt 约束归约）
    buffer_type  dt_send_pair, dt_recv_pair;
    // 持久化 host mirrors（P3/O-B）
    buffer_type  monoq_dxi_h, monoq_deta_h, monoq_dzeta_h;
    buffer_type  sbn_fx_h, sbn_fy_h, sbn_fz_h;
    // T2：MonoQ staged boundary 元素索引（三阶段重叠）
    Kokkos::View<Index_t*> interiorElems, rowColBoundaryElems, planeBoundaryElems;
};
```

## 四、8-rank 热点分析链

### 4.1 针对性 Profiling（第一轮）

测试配置：`8 ranks, OMP=1, -i 50 -s 30/40`，5 次重复。

| Timer | D1 中位 ms/步 | D1 占比 | 说明 |
|-------|-------------:|-------:|------|
| `dt_allreduce` | 3.247 | 12.07% | 每步全局归约 |
| `sbn_wait_unpack` | 2.147 | 8.15% | SBN 阶段等待+解包 |
| `commsbn_wait` | 2.105 | 7.99% | SBN 实际等待 |
| `monoq_wait_unpack` | 1.909 | 7.22% | MonoQ 阶段等待+解包 |
| `commmonoq_wait` | 1.778 | 6.72% | MonoQ 实际等待 |
| `commsend_pack` | 0.054 | 0.20% | 打包（可忽略） |

关键发现：
- **wait 远大于 unpack**：`SBN` 中 `wait/unpack ≈ 64:1`；`MonoQ` 中 `wait/unpack ≈ 178:1`
- **pack 可忽略**：`commsend_pack` 只占 0.2%，不是瓶颈
- **host staging 不大**：CPU 路径下 `sbn_host_pull/push` 各约 0.1–0.3%
- **`dt_allreduce` 是另一热点**：每步 12% 份额，值得后续单独评估

结论：当前 8-rank 主要热点是 **MPI wait 暴露**，而非打包或 staging。

### 4.2 MonoQ Overlap 分析（第二轮）

新增 `monoq_overlap` 派生计时行，分析 interior 计算窗口 vs residual wait 关系。

| 指标 | D1 中位 | D2 中位 |
|------|--------:|--------:|
| `window_ms`（interior 计算） | 0.491 | 1.262 |
| `recv_wait_ms`（剩余等待） | 1.974 | 3.625 |
| `send_wait_ms` | 0.005 | 0.008 |
| `residual_sync_to_window` | ~3.99 | ~2.91 |

- `window:wait ≈ 1:4`（D1），即 interior 计算窗口只能覆盖约 25% 的接收等待
- `send_wait` 极小，可忽略；主要暴露来自 `recv`

## 五、MonoQ 重叠优化实验

### 5.1 T1：提前 CommRecv(MSG_MONOQ) Post

**改动**：将 `CommRecv(domain, MSG_MONOQ, ...)` 从 `CalcMonotonicQGradientsForElems()` 之后提前到其之前，让接收消息更早进入飞行状态。

**Profile A/B 结果**（`D1/D2` 各 5 次，baseline = T1 前版本）：

| 指标 | D1 baseline | D1 T1 | D2 baseline | D2 T1 |
|------|------------:|------:|------------:|------:|
| `plane_min recv_wait_fraction` | 0.644 | 0.421 | 0.556 | 0.312 |
| `plane_max recv_wait_fraction` | 0.630 | 0.381 | 0.571 | 0.320 |
| `plane_min recv_hidden_ms` | — | +167% | — | +153% |
| `plane_max recv_hidden_ms` | — | +185% | — | +160% |

**Release A/B 结果**（`R1/R2` 各 7 次，`/usr/bin/time -p` 计时）：

| Case | baseline median | T1 median | 变化 |
|------|----------------:|----------:|------|
| R1 (s=30, 7 次) | 1.46 s | 1.47 s | +0.68% |
| R2 (s=40, 7 次) | 3.02 s | 3.07 s | +1.66% |

**结论**：T1 在 profile 层面明显改善了 `plane recv` 生命周期（`recv_wait_fraction` 下降约 0.22–0.25，`recv_hidden_ms` 提升约 150–185%），但在 release wall-time 上尚未体现为速度提升。T1 的机制方向正确，但单独施加时缺乏足够的 interior 计算窗口来消化提前启动的接收。

### 5.2 T2：staged boundary——分段 row/col → plane 计算

**改动**：将 `MonoQ` 的 boundary 计算拆成三段，拉长可在 plane recv 飞行期间执行的有效工作窗口：

```
1. 提前 CommRecv(MSG_MONOQ)
2. CalcMonotonicQGradientsForElems
3. host pull + CommSend(MSG_MONOQ)
4. 计算 interiorElems（不依赖任何 ghost）
5. CommMonoQRowCol：等待/解包 row/col face → push row/col ghost 到 device
6. 计算 rowColBoundaryElems（仅依赖 row/col ghost）
7. CommMonoQPlane：等待/解包 plane face → push plane ghost 到 device
8. 计算 planeBoundaryElems（依赖 plane ghost）
```

**涉及文件**：`src/lulesh-comm.cc`、`src/lulesh-viscosity.cc`、`include/lulesh.h`、`include/lulesh-comm.h`、`include/lulesh-profile.h`、`src/lulesh-profile.cc`

**正确性冒烟**：

- `1 rank, -i 1 -s 5`：`Final Origin Energy = 5.416661e+04`，`MaxAbsDiff = 0`
- `8 ranks, -i 1 -s 3`：`Final Origin Energy = 9.359991e+04`，`MaxAbsDiff = 0`

**Profile 冒烟结果**（`8 ranks, OMP=1, -i 10 -s 30`）：

| 指标 | T1（参考） | T2 |
|------|----------:|----|
| `plane_min recv_wait_fraction` | ~0.42 | **0.108** |
| `plane_max recv_wait_fraction` | ~0.38 | **0.029** |
| `monoq_face_wait_peak` | `plane_min/plane_max` | **`row_max`** |

`recv_wait_fraction` 从 T1 时的 ~0.4 进一步降至 ~0.03–0.11；最慢 face 从 plane 转移到 row，说明 T2 已显著削弱 plane recv 作为主拖尾来源的地位。但正式性能结论仍需 A/B 测试完成。

## 六、dt Allreduce 专项优化（O1/O2/O3）

### 6.1 优化背景

Profiling 数据（8 rank, s=30）显示 `dt_allreduce`（即 `CalcTimeConstraintsForElems` 中的全局 dt 归约）占步时 12–15%，imbalance=1.58，是 P1–P6 之后最大的单一 CPU 热点。原实现基于 `KokkosComm::Experimental::allreduce`，通过 KokkosComm View 缓冲区路由，携带不必要的内存分配和调度开销。

### 6.2 三项优化说明

| 编号 | 名称 | 适用路径 | 核心改动 |
|------|------|---------|---------|
| O1 | 裸 `MPI_Allreduce` | CPU（当前交付） | 用两个 stack `double` + `MPI_Allreduce(…, 2, MPI_DOUBLE, MPI_MIN, …)` 替换 KokkosComm blocking allreduce；去除 `dt_send_pair`/`dt_recv_pair` View 缓冲区 |
| O2 | `MPI_Iallreduce` 流水线 | GPU（`KOKKOS_ENABLE_CUDA` 守卫） | `CalcTimeConstraintsForElems` 末尾发射非阻塞 `MPI_Iallreduce`；`LagrangeNodal` 中在 `CalcVelocity` 前调用 `WaitDtIallreduce`，重叠窗口约 12ms（CalcForce+CommSBN+CalcAccel+ApplyBC） |
| O3 | SBN interior/boundary 节点分组 | GPU（`KOKKOS_ENABLE_CUDA` 守卫） | `CommSetup` 构建 `interiorNodes`/`boundaryNodes` 索引列表；`CommSend` 发出后立即在 device 上计算 interior 节点加速度；`CommSBN` 完成后再计算 boundary 节点加速度 |

**O2/O3 为何只在 GPU 路径启用**：CPU 路径下 `MPI_Iallreduce` 移除了隐式屏障，导致各 rank 失同步，`CommSBN` 等待时间从 2.08ms 膨胀到 6.28ms（+4.2ms），超过 allreduce 节省的 2.6ms，净回退。GPU 路径下 device 内核与 MPI 进展线程真正并行，不存在此问题。

### 6.3 关键实现文件

| 文件 | 改动 |
|------|------|
| `include/lulesh-runtime.h` | 新增 `PostDtIallreduce(double, double)` / `WaitDtIallreduce(double&, double&)` 声明 |
| `src/lulesh-runtime-mpi.cc` | `RuntimeState` 新增 `MPI_Request dt_req`、`double dt_send[2]`、`double dt_recv[2]`；实现 `PostDtIallreduce` / `WaitDtIallreduce`；`FinalizeDistributedRuntime` 排空悬挂请求 |
| `include/lulesh.h` | `DomainComm` 移除 `dt_send_pair`/`dt_recv_pair`；新增 `interiorNodes`/`boundaryNodes` |
| `src/lulesh-comm.cc` | `CommSetup` 移除 dt View 分配；新增构建 `interiorNodes`/`boundaryNodes` 的节点扫描循环；`CommTeardown` 同步清理 |
| `src/lulesh-timestep.cc` | `#ifdef KOKKOS_ENABLE_CUDA`：调用 `PostDtIallreduce`（非阻塞）；`#else`：带 `ProfileScope` 的 `MPI_Allreduce` |
| `src/lulesh-nodal.cc` | 新增索引列表重载 `CalcAccelerationForNodes(domain, nodeList)`；`LagrangeNodal` 中 GPU 路径 O3 split + O2 `WaitDtIallreduce`+`TimeIncrement` |
| `apps/lulesh_main.cc` | GPU-MPI 路径下主循环跳过 `TimeIncrement`（已内化到 `LagrangeNodal`） |

### 6.4 性能结果（CPU 路径，8 rank，s=30，100 步）

| Timer | T1 基准（后） | O1 后 | 变化 |
|-------|-------------:|------:|------|
| `step_total` | 34.24 ms | **30.99 ms** | **−3.25 ms (−9.5%)** |
| `dt_allreduce` | 4.29 ms | 3.22 ms | −1.07 ms (−25%) |
| `sbn_wait_unpack` | 2.08 ms | 1.55 ms | −0.53 ms (−26%) |
| `commsbn_wait` | 2.05 ms | 1.52 ms | −0.53 ms (−26%) |

### 6.6 单变量基准测试与回退

**问题发现**：6.4 节中 O1 构建同时包含了 T2（staged MonoQ boundary），导致 +10.5% FOM 是两项改动的混合收益，并非 O1 单独贡献。为隔离 O1 的真实效果，从 T1 基准（`build-t1-baseline-release/`）仅替换两个目标文件（`lulesh-timestep.cc.o` 和 `lulesh-runtime-mpi.cc.o`）重建单变量二进制。

**单变量测试结果**（8 rank，s=30，各 7 次，交替基准/O1）：

| 构建 | FOM 中位（z/s） | CV |
|------|---------------:|-----|
| T1 baseline | 6309 | 1.1% |
| O1 only | 6315 | 1.3% |
| **差值** | **+0.1%** | 在噪声范围内 |

**混淆变量溯源**：T2 的 `monoq_wait_unpack` 从 2.24 ms → 0.29 ms（−1.95 ms），是之前测量到的 +10.5% FOM 的主要贡献者；O1 的 `dt_allreduce` 节省（约 2.6 ms/步）仅减少了中间耗时，对最终吞吐量没有独立测量到的效果。

**KokkosComm allreduce 开销拆解**（路由路径 `mpi::iallreduce`）：

| 开销项 | 内容 |
|--------|------|
| 真正 MPI 工作 | `MPI_Iallreduce` + `MPI_Wait` |
| 额外 fence | `space.fence()` |
| View 生命周期延伸 | `extend_view_lifetime` × 2（heap 分配 + 原子引用计数 × 4） |
| Kokkos 工具钩子 | `Kokkos::Tools::pushRegion` / `popRegion` |

这些开销合计约 1–2 ms/步，但由于 allreduce 本身就是全局同步点，节省这部分开销并不能改变 step 的关键路径长度。

**O2 CPU 路径回退原因**：移除阻塞 allreduce 后各 rank 失去同步点，`sbn_wait_unpack` 从 2.74 ms 膨胀到 6.28 ms（+4.2 ms），超过 allreduce 节省的 2.6 ms，净损失 −25.9% FOM（s=30）。

**回退决定**：O1/O2/O3 全部回退至 `KokkosComm::Experimental::allreduce`。撤销的文件：`src/lulesh-timestep.cc`、`src/lulesh-nodal.cc`、`apps/lulesh_main.cc`、`include/lulesh-runtime.h`、`src/lulesh-runtime-mpi.cc`、`src/lulesh-comm.cc`。两个构建（`build-kokkos-comm`/`build-profile`）回退后编译验证通过。

## 七、代码质量修复

本周在迁移完整性审查与代码扫描过程中发现并修复以下问题，均为继承自原版 LULESH 2.0 的历史缺陷。

### 7.1 MPI 多进程安全：`exit` → `MPI_Abort`

**问题**：`CalcQForElems` 检测到人工粘度超限（`q > qstop`）时调用 `exit(QStopError)`，仅使触发的单个 rank 退出，其余 rank 继续等待 MPI 通信，导致作业永久挂死。

**修复**（`src/lulesh-viscosity.cc`）：

```cpp
// 修复前
if(idx >= 0) { exit(QStopError); }

// 修复后
if(idx >= 0) {
#if USE_MPI
    MPI_Abort(MPI_COMM_WORLD, QStopError) ;  // 通知所有 rank 集体退出
#else
    exit(QStopError) ;
#endif
}
```

### 7.2 梯度/应变 View 预分配

**问题**：`CalcQForElems` 每步调用 `AllocateGradients`（6 个 View）/ `DeallocateGradients`；`CalcLagrangeElements` 每步调用 `AllocateStrains`（3 个 View）/ `DeallocateStrains`——每步合计 9 次 Kokkos View malloc/free，大小固定。

**修复**：将 `AllocateGradients` 和 `AllocateStrains` 移入 `Domain` 构造函数（`src/lulesh-init.cc`），删除每步的 Allocate/Deallocate 调用，同时从 `include/lulesh.h` 删除两个 `Deallocate*` 死代码方法。

### 7.3 GPU kernel 中 `Kokkos::abort()` 后的死代码

**问题**：`CalcMonotonicQForElemsSubset` 和 `CalcMonotonicQForElems` 两个版本的 `switch` default 分支在 `Kokkos::abort()` 之后还有 `delvm=0; break;`。在 CUDA kernel 中 `Kokkos::abort()` 内部调用 `__trap()`，不保证立即终止执行流；若编译器不识别 `[[noreturn]]` 语义，后续赋值可能被实际执行，以 0 替代正确的邻居梯度值传播入结果。

**修复**（`src/lulesh-viscosity.cc`，12 处）：删除 abort 后的 `delvm/delvp=0; break;`，两个版本统一为：

```cpp
default: Kokkos::abort("CalcMonotonicQForElems: bad XI_M bcMask") ;
```

### 7.4 `planeOnly` 死参数清理

**问题**：`CommRecv` / `CommSend` 各有一个 `bool planeOnly` 参数，所有调用处一律传 `false`，函数内永不读取，是原版 LULESH 2.0 未实现的预留接口。

**修复**：从函数声明（`include/lulesh-comm.h`）、定义（`src/lulesh-comm.cc`）及全部 4 处调用（`src/lulesh-nodal.cc`、`src/lulesh-viscosity.cc`）中删除该参数。

### 7.5 非立方体域假设断言

**问题**：`ApplyAccelerationBoundaryConditionsForNodes` 中 `numNodeBC = (sizeX+1)²`，实际上 symmY/Z 的面大小取决于各自方向的 edgeNodes，若域为非立方体则会越界访问。当前代码始终构造立方体域，假设成立，但未文档化。

**修复**（`src/lulesh-nodal.cc`）：

```cpp
assert(domain.sizeY() == size && domain.sizeZ() == size
       && "ApplyBC: symmetry plane nodesets assume a cubic domain") ;
```
